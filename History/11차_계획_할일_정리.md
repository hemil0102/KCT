## 우선순위 2 — 사용자님 액션만 필요 (코드로 할 수 없는 일)

### 2-1. Supabase RLS 정책 수정 — ✅ 완료(확인됨)

`model_failure` 테이블에 `job = "glossary_example"` 항목을 못 넣던 문제
(`42501` — row-level security policy violation). 사용자가 Supabase
대시보드에서 `INSERT` 정책의 `WITH CHECK`에 `'glossary_example'::text`를
추가했고, 다시 조회한 `pg_policies` 결과로 정확히 반영된 것을 확인했다
(`job = ANY (ARRAY['commentary'::text, 'note'::text, 'glossary_example'::text])`).
남은 건 실기기에서 낱말을 탭했을 때 `model_failure`에 실제로
`job = 'glossary_example'` 줄이 쌓이는지 확인하는 것뿐이다.

### 2-2. 어머니 실사용 테스트

9/5 이후 실제 기기 테스트 기록이 없다. 그 사이 이번 세션 포함 UI·기능
변화가 꽤 쌓였다. 다음 라운드 우선순위를 정하려면 실제로 한 번 써보시고
어디서 걸리는지 봐주시는 게 필요하다.

## 우선순위 3 — 중간 규모 (콘텐츠 작업, 코드는 비교적 단순)

### 3-1. 인물 문항 추가 — ✅ 완료

인물 카테고리 문항이 지금 3개뿐이라, 4지선다에서 오답 3개가 전부 인물인
경우가 아직 안 나온다(`8차_적용_보기섞임_스크롤_문구.md`에 테스트 체크리스트로
이미 명시돼 있음).

**한 것 (11차)** — 첨부해주신 1,130문항 문제집(엑셀)에서 쉬운 문항 위주로 골라
`questions.json`에 20문항을 새로 추가해 총 30 → **50문항**으로 늘렸다.

- 역사 인물 8개 (unit `역사3`) — 세종대왕·이순신·신사임당·왕건·광개토대왕·
  안중근·김구·유관순. 인물 정답이 3개(단군왕검·주몽·안익태)에서 **11개**로
  늘어 4지선다에서 오답 3개가 전부 인물인 경우도 이제 나올 수 있다.
- 정치·민주주의 7개 (unit `민주주의1`, 새 카테고리 `정치`) — 민주주의·국민주권·
  선거권·투표·대통령 임기(5년)·국회의원 임기(4년)·여당.
- 전통 음식·의복 5개 (unit `전통음식1`) — 비빔밥·불고기·한복·김장·김치.
  어머니가 일상에서 익숙할 항목 위주로 골랐다.

문항마다 낱말과 해설(`facts`)까지 기존 문항과 같은 형식으로 채웠고, 지문에
실제로 나오는 낱말만 `glossary`에 넣어(코드로 대조 확인함) 밑줄·탭이 정상
작동하도록 했다. `Question.swift`의 낱말 사전 개수 주석도 최신 값(50문항 중
39개)으로 같이 고쳤다.

### 3-2. 문제집 확충 (50 → 1,130문항) — ⏸ 보류

사용자 판단으로 보류. 어머니께 1,000문항이 갑자기 생기면 당황하실 수
있어서, 무작정 늘리지 않고 **스토리 모드로 구역을 나눠 가면서** 문항을
늘리기로 했다. 실제로 `스토리모드_구상.md`(2026-09-05)에도 정확히 같은
순서가 이미 적혀 있었다 — "① 해설 확인 → ② 문항 확장 → ③ storyID 등
태그 붙이기 → ④ 한 해의 이야기부터 → ⑤ 확장"으로, 문항 확장(②)이 스토리
모드 설계(①·③·④ 다음)보다 뒤에 오게 되어 있다. 그러니 4-1(스토리 모드)이
어느 정도 자리 잡을 때까지는 이 항목을 건드리지 않는다.

## 우선순위 4 — 큰 기능 개발 (설계 + 구현 필요)

### 4-1. 스토리 모드 — 🚧 진행 중 (탭바·진입 흐름 만듦)

`SessionBuilder.swift`에 게이트를 끼울 자리(seam)만 있고 실제 구현은
없었다. 실제 챕터·콘텐츠 설계는 `스토리모드_구상.md`(2026-09-05)에 이미
자세히 정리돼 있다 — 네 줄기(시간 이야기·살아가는 이야기·나라의 뼈대·
한 해의 이야기), `storyID`·`chapterID`·`orderInChapter` 태그, "이야기로
배우고 낱개로 확인한다"는 원칙, 그리고 "① 해설 확인 → ② 문항 확장 →
③ 태그 붙이기 → ④ 한 해의 이야기부터 → ⑤ 확장"이라는 순서까지.

**한 것 (11차)** — 그 문서의 ④번 전, 스토리 모드에 **들어갈 문**부터
만들었다.

- `RootView.swift`를 하단 탭바(`TabView`)로 바꿨다 — "나의 이력"(왼쪽,
  신규 `MyHistoryView`) / "문제 풀기"(오른쪽, 기본 탭). 나열 순서만
  바뀐 것이라 앱을 열었을 때 여전히 "문제 풀기"가 보인다.
- `MyHistoryView.swift` — 지금까지 맞힌 누적 개수·마스터 개수를
  `ResultScreen`과 같은 방식(`@Query`)으로 보여주고, "스토리 모드
  시작하기" 버튼을 둔다.
- `StoryModeView.swift` — 아직 챕터 콘텐츠가 없으니 "준비 중이에요" 안내
  화면만 두고, 앞으로 생길 네 줄기 이름만 미리 보여준다. 들어오면 하단
  탭바가 숨고(`.toolbar(.hidden, for: .tabBar)`), 기본 뒤로가기 버튼으로
  나의 이력으로 나가면 탭바가 다시 보인다.
- `PracticeHomeView.swift`(신규) — "문제 풀기" 탭의 메뉴 화면. "종합 연습"
  버튼 하나를 두고, 누르면 `QuizView`로 들어간다.
- `QuizView.swift` — 이제 `PracticeHomeView`의 "종합 연습"에서
  `NavigationLink`로 들어오는 화면이 됐다. 들어오면 하단 탭바가 숨고,
  기본 뒤로가기 버튼 대신 왼쪽 위 X 버튼(`dismiss`)으로 나가면
  `PracticeHomeView`로 돌아가며 탭바가 다시 보인다.

즉 두 탭 모두 "메뉴 화면 → 실제 화면" 2단 구조가 됐다 — 각 메뉴 화면
(`MyHistoryView`·`PracticeHomeView`)에서 다음 화면(`StoryModeView`·
`QuizView`)으로 들어가면 하단 탭바가 숨어 "지금은 이 흐름에 집중하는
중"임을 보여주고, 나오면 다시 나타난다.

**다음 순서** — `스토리모드_구상.md`의 ④번(국경일·명절 문항으로 "한 해의
이야기" 줄기 하나를 먼저 만들어 보는 것). 지금 `questions.json`에 이미
국경일 6개·명절 5개가 있어서 재료는 충분하다. 다만 그 전에 문서가 요구한
"④ 를 먼저 하는 이유 — 한 줄기를 끝까지 만들어 봐야 이 방식이 통하는지
안다"는 원칙대로, 카드(읽는 화면) 문구·마디 나누기·`SessionBuilder`와의
충돌(진척은 공유하되 순서만 이야기가 정하는 문제) 같은 설계 지점을 먼저
사용자와 정하고 시작해야 한다.

### 4-4. 정답 해설 모달 — ✅ 완료

맞혔을 때도 오답 해설과 같은 모양의 모달이 뜨도록 했다. 새로 만들지
않고 기존 것을 최대한 그대로 재활용했다.

- `QuizSession.swift` — `CorrectCommentary`(정답·해설만 있고 고른 답 줄은
  없다) 구조체와 `correctFeedback` 상태, `presentCorrectFeedback(for:)`·
  `dismissCorrectFeedback()`를 추가했다. `gradeCurrent()`의 정답 분기가
  예전에는 곧바로 `moveToNextQuestion()`을 불렀는데, 이제 오답 분기와
  똑같이 모달을 띄우고 「다음 문제」를 눌러야 넘어간다.
- 해설 문장은 **새 프롬프트를 만들지 않고** 오답 해설의 정답 비교 부분을
  만들던 `CommentaryWriter.write(for:)`를 그대로 호출한다 — "이 답이 왜
  맞는지"는 맞고 틀리고와 무관하게 같은 `Question.facts`에서 나오는 같은
  문장이기 때문이다.
- `Screens/CorrectAnswerSheet.swift`(신규) — `FeedbackSheet`의 「✅ 정답」
  줄(배지·카드·글꼴·시트 크기 `.medium`=화면 절반)을 그대로 가져와 한
  줄짜리 모달로 만들었다. `FeedbackSheet.swift`의 `BodyStyle`을
  `private`에서 내부 접근으로 바꿔 두 파일이 같은 스타일을 공유한다.
- `QuizView.swift` — `session.correctFeedback`을 위한 `.sheet(item:)`을
  오답용 시트와 별도로 추가했다. 한 문제는 맞거나 틀리거나 둘 중
  하나라 두 시트가 동시에 뜨는 일은 없다.

### 4-5. 낱말 사전 모달에 닫기 ✕ 추가 — ✅ 완료

`GlossaryPanel.swift` 오른쪽 위에 ✕ 버튼을 다시 넣었다. 예전(9차)에는
배경 탭·답 선택 같은 암묵적 닫기만 남기고 일부러 뺐던 버튼인데, 이번에
명시적인 닫기 방법도 하나 더 달라는 요청을 받아 되살렸다. 색은 새로
만들지 않고 이 모달의 낱말 배지와 같은 조합(연라벤더 배경 +
`wordBadgeText`)을 그대로 썼다.

정답·오답 해설 모달(`CorrectAnswerSheet`·`FeedbackSheet`)에는 X를 넣지
않았다 — 이 둘은 "다음 문제"를 눌러야만 넘어가는 고정 모달이라는 게
사용자님의 명확한 의도였다.

### 4-6. 지문을 화면 위 절반 안으로 — ✅ 완료

정답·오답 해설 모달이 화면 아래 절반(`.presentationDetents([.medium])`)을
덮기 때문에, 모달을 내리지 않고도 문제 지문을 같이 볼 수 있어야 한다는
요청. 짧은 지문은 그대로, 길어서 절반을 넘으면 글꼴을 줄인다.

- `KoreanText.swift` — `fittingFont(for:baseFont:minFontSize:maxHeight:width:lineSpacing:)`
  를 추가했다. 기본 글꼴(30pt)로 쟀을 때 주어진 높이를 넘으면 `minFontSize`
  (20pt)에 닿을 때까지 1pt씩 줄여 가며 다시 재고, 절반 안에 드는 가장 큰
  크기를 돌려준다. 실제 줄바꿈과 같은 값이 나오도록 `updateUIView`와 같은
  문단 스타일(`hangulWordPriority`)로 `NSAttributedString.boundingRect`를 쓴다.
- `QuestionScreen.swift` — `content(for:)`를 `GeometryReader`로 감싸 이 화면의
  실제 크기(탭바·내비게이션 바를 이미 숨겼으므로 거의 화면 전체)를 읽고,
  그 세로 크기의 절반을 `questionFont(for:screenWidth:screenHeight:)`에 넘겨
  글꼴을 고른 뒤 `KoreanText`에 적용한다.
- 최소 글꼴 20pt는 제가 임의로 정한 값이다(더 줄이면 어머니가 읽기 힘들어질
  것 같아서) — 실기기에서 실제로 가장 긴 지문을 띄워 보고 너무 작다 싶으면
  알려주시면 조정하겠다.
- `NSAttributedString.boundingRect`로 재는 높이는 실제 `UILabel` 렌더링과
  근사치다(강조 따옴표 삽입 같은 자잘한 처리는 재는 쪽에서 생략했다) —
  아주 드물게 한두 pt 오차가 있을 수 있지만, "화면 절반 안"이라는 목적에는
  차이가 없다.

### 4-7. 정답 해설 모달 — 접힘/펼침 두 박자로 재설계 — ✅ 완료

문제를 맞혔을 때 뜨는 `CorrectAnswerSheet`를 한 박자짜리(해설 바로 표시)에서
두 박자짜리로 바꿨다. 이제 처음엔 **접힌 채로** "잘 맞추셨어요!" 한 줄과
「정답 해설 보기」·「다음 문제」 두 버튼만 보여주고, 「정답 해설 보기」를
눌러야 시트가 `.medium`(화면 절반)으로 커지며 실제 해설이 나온다. 해설이
궁금하지 않으면 접힌 채로 바로 「다음 문제」를 눌러 넘어갈 수 있다.

- `CorrectAnswerSheet.swift` — `GlossaryPanel`에서 이미 쓰던 접힘/펼침
  패턴(`selectedDetent` 상태 + `.presentationDetents([.height(collapsedHeight),
  .medium], selection:)` + `onChange(of: selectedDetent)`로 `isExpanded` 토글)을
  그대로 가져왔다. `body`가 `isExpanded`에 따라 `collapsedContent` /
  `expandedContent` 중 하나를 그린다. `expandedContent`는 예전 버전(제목 +
  ✅ 카드 + 다음 문제)과 내용이 같다.
- 접힌 높이는 `collapsedHeight: CGFloat = 260`으로 **어림잡아** 정했다 —
  "잘 맞추셨어요!" 한 줄 + 버튼 두 개(각 64pt) + 여백을 계산한 값인데,
  실기기에서 위아래 여백이 어색하면 조정이 필요할 수 있다(GlossaryPanel의
  collapsedHeight도 같은 방식으로 잡은 값이었다).
- 해설 생성(Foundation Model 호출)은 접힘 상태와 **무관하게** 시트가 뜨자마자
  바로 시작한다(`QuizSession.presentCorrectFeedback(for:)`는 그대로) — 그래서
  「정답 해설 보기」를 눌렀을 때 이미 해설이 준비돼 있는 경우가 많다.
- 버튼 두 개의 무게를 다르게 뒀다: 「다음 문제」는 다른 화면과 같은
  `PrimaryActionButton`(시그니처 채움 알약)을 그대로 쓰고, 「정답 해설 보기」는
  흰 알약 + 시그니처 글자로 된 새 버튼(이 파일 안에서만 씀, 재사용 컴포넌트로
  분리하지 않음)을 만들었다 — 이 창의 기본 동작은 "계속 진행"이고 해설을
  보는 것은 원하면 고르는 부가 행동이라고 판단해서다. `ChoiceButton`은 선택지
  버튼용이라 여기 맞지 않아 새로 만들었다.
- `QuizView.swift`의 호출부(`CorrectAnswerSheet(feedback: feedback) {
  session?.dismissCorrectFeedback() }`)는 손대지 않았다 — 새 `init`의
  `startsExpanded`가 기본값 `false`라 그대로 호환된다.

### 4-8. 낱말 창 닫기 ✕ — 배경 없애고 손잡이(^)와 색·크기 맞춤 — ✅ 완료

`GlossaryPanel`의 닫기 ✕ 버튼에서 원형 배지 배경(연라벤더)을 없애고, 위쪽
손잡이(`dragHandle`, 넓적한 "^" 모양)와 같은 색·굵기로 맞췄다.

- 색 : `AppColor.wordBadgeText` + `wordBadgeBackground` 배지 조합 → 배경 없이
  `Color.white.opacity(0.4)` 하나만 — dragHandle의 `Color.white.opacity(0.4)`
  스트로크와 정확히 같은 값이다.
- 크기 : 15pt → 17pt로 살짝 키웠다. dragHandle은 48×10 크기에 4.8pt 굵기
  스트로크라 ✕ 아이콘과 1:1로 잴 수 있는 값은 아니지만, 배경이 없어진 만큼
  같은 흰색·굵은 획으로 존재감이 비슷해지도록 살짝 올렸다.
- 탭 영역(32×32)은 그대로 뒀다 — 눈에 보이는 배경만 없앤 것이라 실수로
  누르기 어려워지지는 않는다.

정확히 ✕ 글자 위를 눌러야만 닫히고 주변은 반응하지 않는다는 후속 피드백을
받아, 탭 인식 범위를 32×32 → **44×44**(Apple 권장 최소 터치 영역)로 넓히고
`.contentShape(Rectangle())`를 추가했다 — 배경이 사라진 뒤로는 SwiftUI가
✕ 글자의 가느다란 획에만 탭을 반응시켜서, `.contentShape`가 없으면 프레임을
키워도 여백은 계속 무시된다. 이제 ✕ 주변 여백을 눌러도 닫힌다.

✕ 색은 이어서 핑크(`Color.pink`, 시스템 기본값)로 바꿨다 — dragHandle과
같은 흰색 계열로 맞췄던 색을 대비가 더 또렷한 핑크로 바꿔 달라는 요청이었다.
기존 팔레트(`AppColor`)에는 이 정도로 선명한 핑크 톤이 없어서(가장 가까운
`wrongAccent`는 흰 카드 위 글자색으로 고른 어두운 로즈색이라 이 창의 짙은
보라 배경 위에서는 잘 안 보일 것 같았다) 새 토큰을 만들지 않고 SwiftUI
시스템 색 `Color.pink`를 그대로 썼다.

### 4-9. 낱말 창 ✕ 제거 → 펼쳤을 때 하단 「닫기」버튼으로 — ✅ 완료

`GlossaryPanel`의 오른쪽 위 ✕를 완전히 없애고, 대신 **시트를 펼쳤을 때만**
맨 아래에 「닫기」버튼을 새로 뒀다.

- 접힌 채로는 원래도 안내 문구를 탭/스와이프해 펼치거나, 배경을 탭하거나
  답을 골라 닫을 수 있어 ✕가 굳이 필요 없었다. 문제는 **펼친 뒤**였다 —
  펼치면 그 안내 문구 자리가 스크롤 제스처로 바뀌어서, 명시적으로 닫을
  방법이 ✕ 하나뿐이었다. 그래서 ✕를 없애는 대신 그 역할을 펼쳤을 때만
  나오는 하단 버튼으로 옮겼다.
- `closeButton`을 흰 알약 + 시그니처 글자색으로 다시 그렸다 — `CorrectAnswerSheet`의
  「정답 해설 보기」와 같은 무게(제목 21pt, 높이 64pt)다. 「다음 문제」같은
  시그니처 채움 버튼(`PrimaryActionButton`)만큼 무겁게 두지 않은 건, 배경을
  눌러도 답을 골라도 똑같이 닫히는 자리라 "반드시 눌러야 하는" 버튼은
  아니기 때문이다.
- `body`에서 `.overlay(alignment: .topTrailing)`를 지우고, `if showsExample { closeButton }`
  형태로 스크롤뷰 아래에 조건부로 둔다. `showsExample`이 이미
  `onChange(of: selectedDetent)` 안 `withAnimation`으로 바뀌므로, 버튼이
  나타나고 사라지는 것도 같은 애니메이션을 그대로 탄다 — 따로 트랜지션을
  추가하지 않았다.
- `QuestionScreen.swift`의 호출부(`GlossaryPanel(...)`)는 `onClose` 시그니처가
  그대로라 손대지 않아도 된다.

### 4-10. 「맞는 짝을 연결해보세요」 연결 문제 — ✅ 1차 구현 완료 (세션 배치는 미완)

국경일 5개 ↔ 날짜 5개처럼, 여러 낱말 쌍을 한 번에 맞히는 새 문제 유형을
Xcode 프로젝트에 실제로 추가했다. 웹으로 만든 데모 3안 중 "큰 글씨 단계형"을
확정해 그대로 옮겼다.

- **재활용 여부** — `questions.json`의 `Question`/`ModePayload`는 재활용할 수
  없다고 결론 냈다. `Question`은 한 사실 = 한 답 구조라 오답 보기를 전체
  문제은행에서 무작위로 뽑는데, 연결 문제는 "이 세트의 N쌍"이 닫힌 묶음으로
  고정돼야 한다. 그래서 완전히 별도의, 나란히 있는 구조를 새로 만들었다.
- **새 파일 4개**
  - `Data/MatchingSet.swift` — `MatchingPair`(left/right 한 쌍), `MatchingSet`
    (id·category·unit·pairs), `MatchingSetPayload`(matchingSets.json 최상위 모양).
  - `Data/matchingSets.json` — 국경일 세트 1개(버전 1). `questions.json`은
    건드리지 않았다.
  - `Data/MatchingSetCatalog.swift` — `QuestionCatalog`와 같은 자리를 하는
    보관소. "받아 둔 것 먼저, 없으면 번들" 규칙을 그대로 따른다.
  - `Screens/MatchingQuestionScreen.swift` — 실제 화면. 상단 X + 회차 진행
    막대, 고정 제목 "맞는 짝은 연결해보세요.", 왼쪽·오른쪽 카드 열, 맞으면
    시그니처 보라 선(체크 아이콘 없음), 틀리면 테두리·글자가 빨갛게 흔들림,
    하단 검정 토스트 안내("왼쪽에서 용어를 골라주세요." / "알맞은 오른쪽
    용어를 골라 연결하세요."), `PrimaryActionButton` 재사용한 "다음" —
    5쌍을 다 맞히기 전엔 눌러도 흔들리며 안내만 뜨고, 다 맞히면 활성화돼
    바로 다음 문제로 넘어간다(오답 해설 없음).
- **왼쪽·오른쪽 순서는 화면이 새로 생길 때마다 각각 따로 무작위로 섞인다** —
  `init`에서 `pairs.enumerated()`를 왼쪽용·오른쪽용으로 독립적으로
  `.shuffled()`한다. 같은 순번(`Slot.id`)을 가진 왼쪽·오른쪽 카드끼리가
  정답이라, 글자를 비교하지 않고도 채점된다.
- **진행 막대를 이 화면 안에서 따로 그린 이유** — 이 문제는 회차의 7문제 중
  하나로 섞여 들어갈 예정이고, "5쌍을 다 맞혀야" 회차 진행 막대 칸이
  올라가야 한다는 요청이 있었다. 기존 `SessionProgressBar`는 "지금 이
  칸도 이미 채워진 것"으로 그리는 2단계(채움/안 채움) 구조라, "아직(회색) ·
  지금 푸는 중(옅은 보라) · 다 맞힘(진한 보라)" 3단계가 필요한 이 화면에는
  맞지 않았다. `SessionProgressBar` 자체는 손대지 않고, 이 화면 안에 같은
  색 토큰(`AppColor.signature`/`softBackground`/`disabledBackground`)으로
  작은 진행 막대를 따로 그렸다.
- **아직 안 한 것** — 회차(7문제: 1·7번 쉬움, 3·4·5번째 중 무작위 한 자리에
  이 연결 문제, 6번째는 미구현 음성 입력 문제) 안에 자동으로 끼워 넣는 배치
  로직은 `SessionBuilder` 쪽 결정이 더 필요해 이번엔 붙이지 않았다. 지금은
  `KCTApp`이 `MatchingSetCatalog`를 읽어 환경에 실어만 두었고,
  `MatchingQuestionScreen`은 `MatchingSet` 하나 + `onClose`/`onComplete`
  클로저만 주면 어디서든 바로 쓸 수 있는 상태다.

### 4-11. 연결 문제를 실제 회차에 끼워 넣기 (5문제 → 7칸) — ✅ 완료

4-10에서 화면·데이터까지는 만들었지만 **회차에 연결한 적이 없어서** 앱에서는
계속 예전 5문제 회차만 나왔다. 그 배선을 이번에 했다.

- **회차를 「칸(slot)」으로 센다.** 연결 문제는 `Question`이 아니라 `QuizItem`
  으로 만들 수 없어서 `items`에 담기지 않는다. 그래서 `QuizSession`이 회차를
  칸으로 세고, 그중 한 칸만 연결 문제로 비워 둔다.

  ```
  칸:    0      1      2          3      4      5      6
       [문제] [문제] [연결문제]  [문제] [문제] [문제] [문제]
  items: 0      1       —         2      3      4      5
  ```

  `currentIndex`는 이제 **칸 번호**이고, `items`를 찾을 때만 `itemIndex(for:)`가
  한 칸 당겨 본다. 연결 문제 칸에서는 `current`가 `nil`이라 `submitCurrent()`·
  낭독 같은 일반 문제용 경로가 저절로 비활성된다 — 그쪽 코드를 고치지 않아도
  된 이유다.
- **`QuizSession`** : `size` 기본값 5 → **7**. `matchingSet`·`matchingSlot`
  상태와 `slotCount`·`isMatchingSlot`·`completeMatchingSlot()`을 새로 뒀고,
  `isFinished`·`isLastQuestion`·`current`·`isEmpty`를 칸 기준으로 바꿨다.
  `start()`에서 연결 문제 한 세트를 뽑고(있으면) 일반 문제를 한 칸 덜 뽑은 뒤,
  3·4·5번째(0부터 세면 2·3·4) 중 한 칸을 무작위로 그 자리로 정한다.
- **`QuizView`** : 환경에서 `MatchingSetCatalog`를 받아 세션에 넘기고,
  `screen(for:)`에 `session.isMatchingSlot` 분기를 더해 `MatchingQuestionScreen`을
  띄운다. 다 맞히면 `completeMatchingSlot()`으로 다음 칸으로 간다 — 해설 창을
  거치지 않는다.
- **`QuestionScreen`** : 진행 막대의 총 칸 수를 `session.items.count` →
  `session.slotCount`로 바꿨다. 안 바꾸면 연결 문제가 낀 회차에서 막대 칸이
  하나 모자란다.
- **프리뷰** : `QuizView`·`RootView`·`PracticeHomeView` 프리뷰에
  `.environment(MatchingSetCatalog.loaded())`를 더했다. 환경 값이 없으면
  프리뷰에서 그 화면에 들어가는 순간 죽는다.
- **1·7번이 쉬운 문제인 것은 저절로 유지된다.** `SessionBuilder.shapeRound()`가
  뽑아 온 일반 문제의 첫·마지막을 격려용 2지선다로 두는데, 연결 문제가 항상
  가운데(3·4·5번째) 칸에 들어가므로 그 첫·마지막이 회차의 1번 칸과 7번 칸에
  그대로 떨어진다.
- **아직 남은 것**
  - 6번째 칸의 음성 입력 문제 — 유형 자체가 없어서 지금은 일반 문제가 온다.
  - 결과 화면 문구는 `session.items.count` 기준이라 연결 문제가 낀 회차에서는
    「오늘 **6**문제 중 N개 맞혔어요」로 나온다. 연결 문제는 채점 대상이
    아니라서 숫자 자체는 맞지만, 진행 막대는 7칸이었으므로 어머니께 어떻게
    보이는 게 나은지는 따로 정해야 한다.

### 4-12. 연결 문제 화면 — 제목이 안 보이던 것 · 낱말 사이 공백 — ✅ 완료

실기기에서 상단 제목만 통째로 안 보인다는 제보. **글자가 빠진 게 아니라
안 보이는 것**이었다 — 화면을 재어 보니 제목이 차지하는 세로 공간(위 여백 24 +
글자 높이)은 그대로 있고 글자만 없었다.

- **원인** : 이 화면에서 **제목만 글자색을 안 정해 둬서** 기본값(`.primary`)이
  됐다. 기기가 다크 모드면 `.primary`는 흰색이 되는데, 이 앱은 배경을 전부
  흰색으로 고정해 두었기 때문에(`QuizView`의 `.background(Color.white)`, 카드의
  `.white` 등) **흰 배경 위 흰 글자**가 되어 글자만 사라진다. 앱의 다른 글자들
  (`ChoiceButton`·`KoreanText`·`ResultScreen`·`StoryModeView` …)은 전부 `.black`을
  직접 박아 두고 있어서 이 문제를 안 겪었다 — 이 화면의 제목만 그 관례에서 빠져
  있었다.
- **고침** : 제목에 `.foregroundStyle(.black)`을 명시. 이제 이 화면의 글자 넷
  (제목·카드·토스트·버튼)이 모두 색을 직접 정한다.
- **문구** : "맞는 짝은 연결해보세요." → **"알맞은 짝을 연결해보세요."**
- **공백** : 좌우 열 사이 56 → **76**, 줄 사이 14 → **18**. 선이 지나갈 자리를
  넓히고, 어느 줄을 고르는지 헷갈리지 않게 했다.

> 앞으로 이 앱에 글자를 새로 넣을 때는 **색을 반드시 직접 정한다.** 이 앱에는
> 다크 모드 대응이 없고 배경만 흰색으로 고정돼 있어서, 색을 안 정한 글자는
> 개발자 기기(라이트 모드)에서는 멀쩡히 보이다가 어머니 기기가 다크 모드면
> 그 글자만 사라진다.

### 4-13. 지문 글꼴 줄이기가 안 먹던 것 — 기준을 잘못 재고 있었다 — ✅ 완료

"지문이 화면 위 절반을 넘으면 글꼴을 줄인다"(11차 후속 2)가 실기기에서 안
먹는다는 제보. **규칙은 돌고 있었지만 재는 기준이 틀려 있었다.**

- **원인** : `maxHeight: screenHeight / 2` 로만 재서, **지문 자체의 높이**가
  절반보다 작은지만 봤다. 그런데 지문은 화면 맨 위에서 시작하지 않는다 —
  위쪽에 바깥 여백(24) + 헤더 줄(44) + 지문 위 여백(32) = **100pt**를 이미
  쓰고 시작한다. 그래서 「높이는 절반 안이지만 끝나는 자리는 절반을 한참
  넘는」 상태가 생긴다.

  고조선 문항(84자)으로 재 보면:

  | | 값 |
  |---|---|
  | 30pt 일 때 지문 높이 | 8줄 · 약 344pt |
  | 옛 기준값 (`screenHeight/2`) | 376pt |
  | 판정 | 344 ≤ 376 → **안 줄임** |
  | 실제로 지문이 끝나는 자리 | 59(안전영역) + 100 + 344 = **503pt** (화면 절반은 422pt) |

- **고침** : 기준을 `screenHeight * 0.5 - questionTopInset(100)` 으로 바꿨다.
  같은 문항이 이제 **27pt · 7줄 · 275pt**로 줄어 화면 절반 언저리에서 끝난다.
- 새 상수 셋을 뒀다 — `questionTopInset`(지문 위가 쓰는 높이), 
  `questionHeightRatio`(지문 몫 비율, 기본 0.5 — 더 작게 하려면 이 값만 내린다),
  `minQuestionAreaHeight`(작은 기기에서 남는 높이가 음수가 되는 것 방지).

> 교훈 : "절반을 넘지 않게" 같은 규칙은 **무엇의 절반인지**와 **어디서부터
> 재는지**를 같이 적어야 한다. 높이만 재면 시작점이 빠진다.

### 4-14. 지문이 여전히 절반을 조금 넘던 것 · 헤더 올리기 · 양쪽 정렬 — ✅ 완료

4-13을 넣고도 "조금 절반을 넘는다"는 제보. 재 보니 **두 가지가 겹쳐 있었다.**

1. 보내주신 화면의 글자를 재니 아직 **30pt** 였다 — 그 빌드에는 4-13이 안 들어가
   있었다.
2. 그런데 4-13만으로도 **모자랐다.** 같은 문항이 27pt·7줄·275pt가 되어 끝나는
   자리가 434pt — 물리 화면 절반(422pt)을 12pt 넘는다. 기준으로 쓰는
   `screenHeight`가 상태바·홈 인디케이터를 뺀 값(751)이라, 그 절반은 눈에 보이는
   화면의 절반보다 아래에 있기 때문이다.

| | 기준값 | 고른 글꼴 | 지문이 끝나는 자리 |
|---|---|---|---|
| 고치기 전 | 376pt | 30pt · 8줄 | 503pt ✗ |
| 4-13 | 276pt | 27pt · 7줄 | 434pt ✗ (12pt 초과) |
| **4-14** | **268pt** | **26pt · 7줄** | **409pt ✓** |

- **`questionBottomMargin`(24pt) 신설** — 안전 영역 때문에 생기는 오차와 줄바꿈
  계산 오차를 함께 흡수한다. 절반 선에 딱 붙이지 않는다.
- **헤더 줄을 위로** — `content(for:)`의 `.padding(24)`를 방향별로 나눠 위쪽만
  **8**로 줄였다(좌우 24는 그대로 — `questionHorizontalInset` 계산이 걸려 있다).
  X·진행 막대가 16pt 올라가고, 그만큼 지문도 위로 올라온다.
  `questionTopInset` 도 100 → **84**(8+44+32)로 갱신.
- **지문 양쪽 정렬** — `KoreanText`의 `paragraph.alignment` 를 `.left` → `.justified`.
  오른쪽 끝이 들쭉날쭉해 덩어리가 기울어 보인다는 요청. 줄 안의 **띄어쓰기 폭만**
  늘리는 방식이라 글자는 안 늘어나고, 띄어쓰기가 거의 없는 줄은 그 줄만 짧게
  끝난다(늘릴 자리가 없어서). 되돌리려면 그 한 줄만 `.left` 로.
  높이를 재는 `measuredHeight` 의 문단 스타일에도 같은 정렬을 넣어 실제와 맞췄다.

> 모달은 `FeedbackSheet` 가 `.medium`, `CorrectAnswerSheet` 가
> `[.height(collapsedHeight), .medium]` 이라 **펼쳤을 때 화면 아래 절반**을 덮는다.
> 그래서 "절반" 이 기준인 것이 맞다.

### 4-15. 양쪽 정렬을 직접 만들기 — 글자 사이 말고 띄어쓰기만 늘린다 — ✅ 완료

4-14에서 넣은 `paragraph.alignment = .justified` 가 **글자와 글자 사이를 전부**
벌려서 「임진왜란」이 「임 진 왜 란」처럼 나왔다. 벌어지는 정도도 줄마다 달라
낱말 덩어리가 사라졌다 — 어르신이 읽기에 가장 나쁜 모양이다.

- **원인** : CoreText 는 한글을 CJK 로 보고 **모든 글자 사이**에 남는 폭을 나눠
  준다. 라틴 문자처럼 띄어쓰기만 늘리지 않는다. (4-14에 "띄어쓰기 폭만 늘린다"고
  적었던 것은 틀린 설명이었다.)
- **고침** : 정렬은 `.left` 로 되돌리고, `KoreanText.justifyBySpaces(_:width:)` 를
  새로 만들어 **직접** 오른쪽 끝을 맞춘다.
  1. TextKit 으로 줄바꿈을 미리 계산해 줄마다 (실제로 쓴 폭, 글자 범위)를 모은다
  2. 줄마다 모자라는 폭을 **그 줄의 띄어쓰기 개수로 나눠** `.kern` 으로 준다
  3. 마지막 줄은 안 늘린다(양쪽 정렬의 관례). 줄 끝에 걸린 띄어쓰기도 뺀다
  4. 0.5pt 는 남긴다 — 폭을 딱 맞추면 반올림 때문에 줄이 다시 나뉠 수 있다
- **폭은 부르는 쪽이 값으로 내려준다** (`justifyWidth`). 라벨의 `bounds` 는
  `updateUIView` 시점에 아직 최종값이 아닐 수 있어서다. `QuestionScreen` 은
  글꼴 크기를 정할 때 쓰는 폭(`screenWidth - questionHorizontalInset`)과 **같은
  값**을 준다 — 두 계산이 어긋나면 줄이 다시 나뉜다.
- `.kern` 은 글자 **번호**를 바꾸지 않으므로, 먼저 구해 둔 밑줄·형광펜·낱말 배경
  범위가 그대로 맞는다. 그래서 이 처리를 맨 뒤에 둔다.

> **남는 한계** — 한 줄에 띄어쓰기가 하나도 없으면(긴 낱말 하나로 찬 줄) 늘릴
> 자리가 없어 그 줄만 짧게 끝난다. 띄어쓰기가 한두 개뿐인 줄은 그 자리에 남는
> 폭이 다 몰려 낱말 사이가 꽤 벌어진다. 그게 거슬리면 `justifyWidth` 를 안
> 넘기면 된다 — 그 즉시 예전처럼 왼쪽 정렬(오른쪽 끝 들쭉날쭉)로 돌아간다.

> **삽질 기록** — `justifyWidth` 프로퍼티를 처음엔 `selectedWordTextColor` 뒤에
> 선언했는데, 호출부에서는 `font` 다음에 넘기고 있었다. 구조체의 멤버와이즈
> 이니셜라이저는 **선언 순서대로** 인자를 받으므로 이대로면 컴파일이 안 된다.
> 선언을 `lineSpacing` 뒤로 옮겨 순서를 맞췄다.

### 4-16. 양쪽 정렬 최종 — 글자 단위 줄바꿈 + `.justified` — ✅ 완료

4-15(띄어쓰기만 늘리기)도 낱말 사이가 너무 벌어졌다. **근본 원인은 줄바꿈
규칙이었다.**

- **원인** : 단어 단위로만 끊으니(`byWordWrapping` + `hangulWordPriority`) 줄 끝에
  **단어 하나만큼**이 통째로 남는다. 그 큰 빈자리를 어디에 밀어 넣든 이상해진다 —
  띄어쓰기에 몰면 낱말 사이가 쩍 벌어지고(4-15), CoreText 에 맡기면 글자 사이가
  전부 벌어진다(4-14).
- **고침** : "꼭 단어별로 줄바꿈 안 해도 된다"는 확인을 받아 **글자 단위 줄바꿈**
  (`byCharWrapping`, `lineBreakStrategy = []`)으로 바꾸고, 정렬은 CoreText 의
  `.justified` 를 그대로 쓴다. 글자 단위로 채우면 남는 폭이 **한 글자보다 작아져서**
  벌리는 양이 눈에 안 띈다. 한글 책·신문도 낱말 중간에서 줄을 바꾼다.

  같은 문항("대한민국 헌법을 만들어 공포한 것을 기념하는 국경일은 무엇입니까?", 26pt):

  | 줄바꿈 | 줄마다 남는 폭 | 틈 하나에 들어가는 양 |
  |---|---|---|
  | 단어 단위 (전) | 61 · 87pt | **5.5 · 8.7pt** |
  | 글자 단위 (후) | 2.5 · 22pt | **0.2 · 1.6pt** |

- 4-15에서 만든 `justifyBySpaces(_:width:)` 와 `justifyWidth` 프로퍼티는 필요가
  없어져 **삭제**했다(호출부 포함).
- `measuredHeight` 의 문단 스타일도 같은 규칙으로 맞췄다 — 여기가 다르면 글꼴
  고르기가 헛돈다.
- 숫자+단위를 붙여 두는 WORD JOINER(`keepingNumbersWithUnits`)는 그대로 둔다.
  글자 단위로 끊으면 "2333년"이 갈라질 수 있어 **오히려 더 중요해졌다.**

> 남는 것 : 낱말 중간에서 줄이 바뀐다. 한글 조판에서는 흔한 모양이지만, 어머니가
> 읽기 불편해하시면 `byWordWrapping` + `hangulWordPriority` 로 되돌리고 정렬을
> `.left` 로 두면 된다(오른쪽 끝은 다시 들쭉날쭉해진다).

### 4-17. 해설을 50자(세 줄)로 줄이기 — ✅ 완료

오답·정답 해설이 길어서 창을 많이 차지한다는 요청. 둘 다 같은 함수
(`CommentaryWriter.write(for:)`)가 쓰므로 한 곳만 고치면 둘 다 바뀐다.

**왜 50자인가** — 해설 본문은 21pt(`noteSize`), 모달 폭에서 한 줄에 약 17자가
들어간다. 50자면 딱 **세 줄**이다.

- **프롬프트** — "세 문장 이내" → "띄어쓰기 포함 50자 이내". 규칙을 둘로 쪼개
  적었다: ② 전체 50자, ③ 한 문장 20자 이내로 두세 문장. ④ "재료를 다 쓰려고 하지
  말고 가장 중요한 것 하나만"을 새로 넣었다 — 이게 없으면 모델이 준 재료를 다
  욱여넣으려다 길어진다.
- **`@Guide`** 설명도 "세 문장 이내" → "띄어쓰기를 포함해 50자 이내" 로 맞췄다.
  생성을 실제로 이끄는 건 이 한 줄이라 프롬프트만 고치면 덜 듣는다.
- **재료 개수 4 → 2** (`materialLimit`). 재료를 넉넉히 주고 짧게 쓰라고 하면 서로
  싸운다. 어느 2개가 뽑힐지는 매번 섞이므로 같은 문항이라도 글은 달라진다.
- **`shortened(_:)` 추가 (안전망)** — 기기 모델은 글자를 못 세서 프롬프트만으로는
  종종 넘긴다. 받아 온 글이 50자를 넘으면 **문장 끝(. ! ?) 기준으로** 잘라 낸다.
  글자 수로 뚝 자르면 「단군왕검은 고조선을 세운」처럼 말이 끊긴 채 남기 때문이다.
  첫 문장 하나가 이미 50자를 넘으면 그 문장은 통째로 남긴다 — 조금 길어도 말이
  끊긴 것보다 낫다.

  | 모델이 준 글 | 자른 뒤 |
  |---|---|
  | 88자 (네 문장) | **47자** — 앞 두 문장만 |
  | 32자 | 그대로 |

> 손대지 않은 것 : 오답 창의 「고르신 답」 한 줄 설명(`describe(_:)`)은 원래
> 한 문장짜리라 그대로 뒀다. 그 줄까지 짧게 하고 싶으면 같은 방식으로 넣으면 된다.

### 4-18. 해설 모달 — 정답은 연두, 오답은 주황 (배경·제목·버튼 한 세트) — ✅ 완료

두 해설 창이 똑같은 보라여서, 창이 뜬 순간에는 맞았는지 틀렸는지를 **글자를
읽어야** 알 수 있었다. 색으로 먼저 알게 바꿨다.

| 창 | 배경 (0.75로 깔림) | 제목 글자 · 버튼 |
|---|---|---|
| 정답 `CorrectAnswerSheet` | 밝은 연두 `#7FBB2E` → 보이는색 `#9FCC62` | **진한 녹색** `#2E6B1F` |
| 오답 `FeedbackSheet` | 밝은 주황 `#E88A1E` → 보이는색 `#EEA756` | **진한 주황** `#94480C` |
| 낱말 `GlossaryPanel` | 시그니처 보라 (그대로) | 흰 글자 (그대로) |

**배경·제목·버튼은 한 세트다.** 배경을 밝게 하면 흰 글자를 못 얹는다 — 연두
배경 위 흰 글자는 1.86:1, 주황 위는 2.04:1 까지 떨어진다. 그래서 제목과 버튼을
같은 계열의 **진한 색**으로 바꿨다. 밝은 바탕 · 진한 글자/버튼의 한 세트다.

| 짝 | 연두 | 주황 |
|---|---|---|
| 배경 위 제목(진한 색) | 3.49 : 1 | 3.23 : 1 |
| 버튼 위 흰 글자 | 6.48 : 1 | 6.58 : 1 |
| 흰 알약 위 진한 글자 | 6.48 : 1 | — |

- 버튼 채움을 바꾸려고 `PrimaryActionButton` 에 `fill` 파라미터를 더했다
  (기본값 = 시그니처). **`action` 앞에** 선언해야 기존 호출부가 그대로 컴파일된다 —
  멤버와이즈 이니셜라이저는 선언 순서대로 인자를 받기 때문이다. 해설 모달 두 곳만
  값을 넘기고, 다른 화면의 버튼은 기본값이라 손대지 않았다.
- 흰 글자를 쓰던 자리 셋(정답 창 「잘 맞추셨어요!」·「정답 해설」, 오답 창 제목)이
  전부 진한 색으로 바뀌었다. 「정답 해설 보기」(흰 알약)의 글자도 보라 → 진한 녹색.
- 낱말 해설 창(`GlossaryPanel`)은 배경이 진한 보라라 흰 글자가 그대로 잘 읽힌다.
  손대지 않았다.
- 빨강이 아니라 주황인 것은 "틀렸다고 몰아붙이지 않는다"는 원칙 때문이다
  (``review`` 가 빨강이 아니라 시그니처인 것과 같은 이유).

### 4-19. 정답 해설 모달 마무리 — 제목 흰색·축하 문구 1.5배·정답 낱말 녹색 — ✅ 완료

- **「잘 맞추셨어요!」** : 진한 녹색 → **흰색**, 크기는 제목(21)의 **1.5배(31.5pt)**.
  `celebrationSize` 상수를 따로 뒀다(`titleSize * 1.5`). 이 줄은 창의 제목이 아니라
  축하 한마디라, 창이 뜬 순간 가장 먼저 눈에 들어와야 한다.
- **「정답 해설」 제목**(펼쳤을 때)도 흰색. 이 창에서 배경 위에 바로 올라가는 글자는
  이 둘뿐이라, 색이 다르면 접었다 펼 때 색이 바뀌어 보인다.
- **정답 낱말이 하늘색 → 녹색.** 배지 배경은 새 토큰 `answerSheetBadge`(옅은 녹색),
  글자는 버튼과 같은 `answerSheetAccent`(진한 녹색)를 그대로 쓴다. 해설 본문 속
  낱말 강조도 같은 색이다.

| | 지금 (파란 톤) | 바꾼 뒤 (녹색 톤) |
|---|---|---|
| 배지 위 낱말 | 4.02 : 1 | **5.29 : 1** |
| 흰 카드 위 낱말 | 5.41 : 1 | **6.48 : 1** |

> **오답 창(`FeedbackSheet`)의 정답 낱말은 하늘색 그대로 뒀다.** 거기서는
> 「고르신 답(분홍) ↔ 정답(하늘)」 두 색을 견주어 읽는 자리라, 한쪽만 녹색으로
> 바꾸면 그 대비가 흐려진다. 이 창에는 견줄 상대가 없어서 창 색에 맞췄다.

> 흰 글자 두 줄은 밝은 연두 배경 위에서 대비가 1.86:1 로 낮다. 31.5pt·21pt 굵은
> 글씨라 읽히지만, 흐리게 느껴지면 ① 배경을 한 단계 어둡게 하거나 ② 그 줄만
> 다시 진한 녹색으로 되돌리면 된다.

### 4-20. 오답 창 오렌지 조정 · 제목 흰색 통일 · 정답 낱말 녹색 · 뒤 화면 잠금 — ✅ 완료

- **오답 창 배경을 더 오렌지로** : `#E88A1E` → **`#F5821E`** (보이는 색 `#F8A156`).
  흰 제목 대비는 2.04 → 2.05:1 로 그대로다 — 더 밝아졌는데 대비가 안 떨어진 건
  색상을 오렌지 쪽으로 돌린 덕이다.
- **「정답 보기」·「다음 문제」 버튼도 오렌지 쪽으로** : `#94480C`(갈색에 가까웠다)
  → **`#B85208`**. 버튼 위 흰 글자 4.94:1, 배경과 2.41:1. 더 진하게 하면 구분은
  또렷해지지만 다시 갈색으로 보인다 — 이 선에서 멈췄다.
- **제목 흰색 통일** : 「오답 해설」·「오답 및 정답 비교 해설」도 흰 글자로. 정답 창의
  흰 제목과 짝을 맞춘 것이다 — 두 창이 같은 자리에 같은 무게의 글자를 둬야 색만
  바뀐 것처럼 보인다.
- **정답 낱말을 두 창 모두 녹색으로** : 오답 창의 「정답」 줄도 `answerSheetBadge`
  (옅은 녹색) + `answerSheetAccent`(진한 녹색)를 쓴다. 이제 그 창은 **「고르신
  답(분홍) ↔ 정답(녹색)」** 으로 읽힌다 — 분홍/하늘색 때보다 뜻이 바로 온다.
  `answerHeader`·`answerAccent`(하늘색)는 **쓰는 곳이 없어졌다**(값은 남겨 둠).

**해설 창이 떠 있을 때 뒤 화면 잠금** — 두 창은 뒤를 어둡게 하지 않고 그대로 비치게
해 뒀는데(`presentationBackgroundInteraction(.enabled)`), 그 대가로 **창이 덮지 않은
위쪽의 보기 버튼이 그대로 눌렸다.** 이미 채점이 끝난 뒤라 답을 바꿔도 결과는 안
바뀌지만, 눌리는데 아무 일도 안 일어나면 고장으로 보인다.

- `QuizSession.isShowingCommentary`(= `feedback != nil || correctFeedback != nil`)를
  새로 두고, `QuestionScreen` 의 본문에 `.allowsHitTesting(!session.isShowingCommentary)`
  를 걸었다.
- `.disabled(...)` 가 아니라 `allowsHitTesting` 인 이유 — disabled 는 버튼 모양을
  흐리게 만들 수 있는데, 여기서는 **보이는 것은 그대로 두고 손가락만 막으면** 된다.
- 낱말 탭도 같이 막힌다. 창이 이미 하나 떠 있어서 낱말 사전 시트는 어차피 못 뜬다.

### 4-21. 해설 길이 40~50자 · 입력형에서 키보드 접고 창 띄우기 — ✅ 완료

**해설 길이에 하한을 뒀다 (4-17 후속).** 50자 "이내"만 있으면 20자짜리도 통과라
창이 허전했다. 이제 **40자 이상 50자 이내**다.

- 프롬프트·`@Guide` 를 "40자 이상 50자 이내"로. **하한은 코드가 못 채운다** —
  짧게 온 글에 말을 보탤 수는 없으니 프롬프트로 부탁하는 수밖에 없다.
- 코드가 하는 일은 `shortened(_:)` 가 **자르다가 40자 밑으로 떨어뜨리지 않게**
  막는 것까지다. 한 문장을 버려서 40자 밑이 될 상황이면 `overflowLimit`(60자)
  까지는 그 문장을 살린다 — 「50자에 맞추려다 25자가 됐다」가 제일 나쁘다.

| 모델이 준 글 | 예전 | 지금 |
|---|---|---|
| 74자 · 네 문장 | 47자 | **45자** |
| 48자 · 둘째 문장이 긺 | 18자(첫 문장만) | **48자** ✓ |
| 51자 · 한 문장 | 51자 | 51자 (문장을 쪼개지 않는다) |

**입력형에서 「다음」을 누르면 키보드부터 접는다.** 예전에는 키보드가 올라온 채로
채점이 끝나 해설 창이 올라왔고, 창이 반쯤 가려진 것처럼 보였다.

- `@FocusState private var isAnswerFieldFocused` 를 두고 `TextField` 에 연결.
  제출 경로를 `submitAnswer()` 하나로 모아 **키보드를 내린 뒤** `session.submitCurrent()`
  를 부른다. 「다음」 버튼과 키보드의 완료(`onSubmit`)가 같은 경로를 쓴다 —
  한쪽만 고치면 다른 쪽에서 키보드가 남는다.
- **답이 비어 안내만 띄울 때는 안 내린다.** 그때는 바로 이어서 입력해야 하므로
  키보드가 남아 있는 편이 맞다.

### 4-22. 해설 창 색을 보라로 되돌림 (4-18 ~ 4-20 색 부분 철회) — ✅ 완료

정답=연두 · 오답=주황으로 갈랐던 것을 **원래 시그니처 보라로 되돌렸다.**
세 창(정답·오답·낱말 해설)이 다시 같은 보라 · 같은 진하기(0.75)다.

**왜 안 됐나 — 밝은 배경이 흰 글자를 못 받친다.** 연두·주황을 배경으로 깔면 흰
글자 대비가 1.9~2.0:1 까지 떨어진다. 그래서 제목과 버튼을 그 계열의 진한 색으로
바꿔야 했는데, 그러면 「다음 문제」가 화면마다 다른 색이 되어 앱의 다른 곳과 따로
놀았다. 창을 구분하려다 버튼의 일관성을 잃은 셈이다.

| 되돌린 것 | 남긴 것 |
|---|---|
| 배경 → `signature.opacity(0.75)` | 「잘 맞추셨어요!」 1.5배 크기 |
| 버튼 → 시그니처 채움 (`fill` 안 넘김) | **정답 낱말 녹색** (배지 + 본문 강조) |
| 「정답 해설 보기」 글자 → 시그니처 | |
| 제목 → 흰 글자 `.opacity(0.96)` (원래 값) | |

- **정답 낱말의 녹색은 남겼다.** 낱말은 흰 카드 위에 올라가므로 창 배경(보라)과
  부딪히지 않고, 「고르신 답(분홍) ↔ 정답(녹색)」이 하늘색일 때보다 뜻이 바로 온다.
  두 창 모두 같다. (원래 하늘색이던 ``answerHeader``·``answerAccent`` 는 계속 미사용.)
- 안 쓰게 된 값(``answerSheetBackground``·``wrongSheetBackground``·``wrongSheetAccent``)과
  `PrimaryActionButton.fill` 파라미터는 **지우지 않고 「현재 미사용」으로 표시**해 뒀다.
  같은 시도를 또 할 때 그 한 줄이면 된다.

> 배운 것 : 창 배경색은 **그 위에 올라가는 글자색까지 한 세트**다. 배경만 바꾸는
> 변경은 없다 — 밝게 하면 글자를 어둡게 해야 하고, 그러면 버튼까지 따라온다.

### 4-23. 해설 길이 40~50자 → 50~70자 — ✅ 완료

| | 전 | 후 |
|---|---|---|
| 하한 `minCharacters` | 40 | **50** |
| 상한 `maxCharacters` | 50 | **70** |
| 자를 때 봐주는 한계 `overflowLimit` | 60 | **80** |
| 프롬프트에 넣는 재료 `materialLimit` | 2 | **3** |

- 해설 본문은 21pt라 한 줄에 약 17자다. 50자 ≈ 세 줄, 70자 ≈ 네 줄 — 창에서
  **서너 줄**로 끝난다.
- 프롬프트의 "짧은 문장 두세 개 · 한 문장 20자" → **"세 개쯤 · 한 문장 25자"**.
- **재료를 2개에서 3개로 올렸다.** 재료가 2개뿐이면 50자를 채우려고 같은 말을
  늘여 쓰게 된다. 길이를 늘릴 때는 **줄 재료도 같이 늘려야** 한다.

### 4-24. 줄 끝에서 갈린 낱말의 점선이 아랫줄에만 안 나오던 버그 — ✅ 완료

「…기념하는 **국** / **경일**은 무엇입니까?」에서 「국」에는 점선이 있는데
「경일」에는 없다는 제보.

- **점선은 그려지고 있었다. 잘려 나간 것이다.** `UnderlineLabel.drawText` 는 줄마다
  따로 선을 긋고 있었고(`enumerateLineFragments`) 그 부분은 멀쩡했다. 문제는
  `KoreanText.sizeThatFits` 가 **뷰 높이에 밑줄 자리를 안 비워 둔 것**이다. 뷰
  높이가 글자 높이와 똑같으니, 마지막 줄 글자 **아래**에 찍는 점은 뷰 밖이라
  그리기 단계에서 통째로 잘린다.

  ```
  underlineAllowance = max(0, gap(2) - lineFragmentPadding(10) + depth(1.5) + 2)
                     = max(0, -4.5) = 0      ← 늘 0이었다
  ```

- **왜 `lineFragmentPadding` 을 빼고 있었나** — 그건 **중간 줄**에서 쓰는 보정값이다
  (`drawText` 의 `correction`). 중간 줄의 line fragment 에는 줄 간격이 붙어 있어
  10을 빼야 「받침 바로 아래」가 나오지만, **마지막 줄은 그 보정을 안 쓴다.**
  정작 잘릴 위험이 있는 건 마지막 줄인데, 거기 기준이 아닌 값으로 여유를 계산하고
  있었다. 마지막 줄 기준으로 고쳤다:

  ```
  underlineAllowance = max(0, gap(2) + depth(1.5) + 2) = 5.5pt
  ```

- 이 버그는 **4-16(글자 단위 줄바꿈)으로 드러났다.** 예전에는 낱말 단위로만 줄을
  바꿔서(`hangulWordPriority`) 낱말이 두 줄에 갈리는 일이 거의 없었다.
- `max(0, ...)` 는 그대로 뒀다 — `underlineGap` 에 음수를 줘서 밑줄을 글자 위로
  올릴 때 뷰가 글자보다 작아지는 것을 막는 장치다.

### 4-25. 해설 길이 50~70자 → 50~60자 — ✅ 완료

`maxCharacters` 70 → **60**, `overflowLimit` 80 → **70**. 프롬프트·`@Guide`·자르기
로직·문서를 전부 맞췄다. 하한(50)과 재료 개수(3개)는 그대로다.

### 4-26. 줄 첫머리에 공백이 남던 것 — 끊어도 되는 자리를 직접 심는 방식으로 — ✅ 완료

「…붉은색이 나쁜 / ␣귀신을 쫓아낸다고…」처럼 **다음 줄이 한 칸 들여쓴 것처럼**
보인다는 제보.

- **원인** : 4-16에서 넣은 `byCharWrapping`(아무 데서나 끊기)은 **띄어쓰기도 한
  글자로 본다.** 그래서 줄 끝에 안 들어간 공백이 다음 줄 첫머리로 넘어가 그대로
  그려진다. 보통의 낱말 단위 줄바꿈은 줄 끝의 공백을 알아서 흡수한다.
- **고침** : 줄바꿈을 `byWordWrapping` 으로 되돌리되, **낱말 안에 「여기서 끊어도
  된다」는 자리를 미리 심는다.** 한글과 한글 사이마다 폭이 0인
  ZERO WIDTH SPACE(U+200B)를 넣는 것이다.

| | 줄 채움 | 줄 첫머리 공백 |
|---|---|---|
| 낱말 단위만 (4-14 이전) | 헐렁함 → 양쪽 정렬이 쩍 벌어짐 | 없음 |
| 글자 단위 (4-16) | 빽빽함 ✓ | **남음** ✗ |
| **지금** | 빽빽함 ✓ | 없음 ✓ |

- `keepingNumbersWithUnits(_:)` → **`preparedForLineBreaks(_:)`** 로 이름을 바꾸고
  역할을 둘로 넓혔다. 한글 사이엔 U+200B(끊어도 된다), 숫자+한글 사이엔 기존
  U+2060(끊지 마라 — "2333년"). **둘 다 폭이 0이라 화면에는 안 보인다.**
- 강조·형광펜·낱말 검색도 같은 전처리를 거친 문자열로 찾으므로 구간이 그대로
  맞는다(원래 그렇게 돼 있었다). 68자 지문이면 폭 0인 글자가 27개 들어간다.
- `measuredHeight` 의 문단 스타일도 같이 맞췄다 — 여기가 실제 렌더링과 다르면
  글꼴 크기 고르기가 헛돈다.

### 4-27. 해설 본문도 지문과 같은 양쪽 정렬로 — ✅ 완료

지문만 양쪽 정렬이고 해설은 왼쪽 정렬이라 두 글의 모양이 달랐다.

- **막힌 지점** : SwiftUI 의 `Text` 는 **양쪽 정렬을 지원하지 않는다**
  (`multilineTextAlignment` 에 `.justified` 가 없다). 그래서 해설도 UILabel 로
  그려야 했다.
- **그러면 줄바꿈 규칙이 두 벌이 된다** — 이번 세션에서 `measuredHeight` 가 실제
  렌더링과 어긋난 일이 이미 두 번 있었다. 그래서 규칙을 새 파일
  **`DesignSystem/KoreanTextLayout.swift`** 로 빼서 한 벌만 두었다.

  | 새 파일에 있는 것 | 하는 일 |
  |---|---|
  | `KoreanTextLayout.prepared(_:)` | 끊어도 되는 자리(U+200B)·끊지 말 자리(U+2060)를 심는다 |
  | `KoreanTextLayout.paragraphStyle(lineSpacing:)` | 양쪽 정렬 + 낱말 단위 줄바꿈 |
  | `JustifiedKoreanText` | 낱말 하나만 색·굵기가 다른 글을 그 규칙으로 그린다 |
  | `Character.isHangul` | (KoreanText 에서 옮겨 옴 — 둘이 같이 쓴다) |

- `KoreanText`(지문)도 이제 그 규칙을 **가져다 쓴다.** 문단 스타일을 만들던 두
  곳과 전처리 함수가 전부 `KoreanTextLayout` 을 부른다.
- 두 창의 `Text(…AttributedString…).modifier(BodyStyle)` 세 자리를
  `justifiedBody(_:word:color:)` 로 바꿨다. 글꼴·색·줄간격은 `BodyStyle` 이 주던
  값 그대로다 — **기다리는 동안 보여주는 글은 여전히 `BodyStyle` 을 쓰므로**, 두
  값이 어긋나면 해설이 도착하는 순간 글자 모양이 튄다.
- 쓰이지 않게 된 `commentaryText`·`noteText`·`highlight(_:word:color:size:)` 는
  두 파일에서 지웠다(합쳐 43줄).

> 남은 차이 : 기다리는 동안 보여주는 한 줄(「잠시만 같이 살펴봐요.」·응원 문구)은
> 여전히 왼쪽 정렬이다. 한 줄짜리라 정렬이 눈에 띄지 않고, 맥동 애니메이션이
> 걸려 있어 건드리지 않았다.

### 4-28. 해설 글의 왼쪽 들여쓰기 없애기 — ✅ 완료

해설 글이 이모지 폭만큼(20 + 사이 10 = **30pt**) 들여쓰여 있었다. 해설이 서너
줄이라 그 들여쓰기가 줄마다 쌓였고, 양쪽 정렬로 오른쪽 끝을 맞춘 뒤로는 왼쪽만
들어가 있어 더 눈에 띄었다.

```
[전]  ✅  [현충일]                   [후]  ✅ [현충일]
          현충은 충성을 드러낸다는          현충은 충성을 드러낸다는 뜻이에요.
          뜻이에요. 현충일은…               현충일은 온 나라가 묵념해요.
```

- `noteRow(...)` 의 구조를 「이모지 칸 | 배지+해설 칸」(HStack 안에 VStack) →
  「이모지와 배지가 한 줄, 그 아래 해설」(VStack 안에 HStack)으로 뒤집었다.
  해설이 카드 안쪽 왼쪽 끝에서 시작하고, 한 줄에 들어가는 글자도 늘어난다.
- 이모지와 배지는 `alignment: .center` 로 나란히 둔다(예전엔 `.top` + 위 여백 1).
- **두 창 모두** 같은 구조라 똑같이 고쳤다.

### 4-29. 밑줄이 한 글자쯤 어긋나던 버그 — 글자와 밑줄을 한 엔진으로 — ✅ 완료

「팥죽」 밑줄이 「죽을」 밑에, 「쑤어」 밑줄이 「어 먹」 밑에 찍혔다. **오른쪽으로
한 글자쯤 밀린 모양**이었다.

- **원인** : `UnderlineLabel` 은 **글자를 UILabel 에게 맡기고**(`super.drawText`)
  **밑줄 자리는 자기가 만든 TextKit 스택으로 계산**하고 있었다. 서로 다른 두 엔진이
  줄을 끊는 자리를 각자 정한 것이다.
  - 예전에는 어긋나지 않았다 — 끊을 수 있는 자리가 띄어쓰기뿐이라 두 엔진이 같은
    답을 냈기 때문이다.
  - 4-26에서 한글 사이마다 끊어도 되는 자리(U+200B)를 심고 양쪽 정렬까지 켜자
    **끊을 수 있는 자리가 촘촘해졌고**, 두 엔진이 서로 다른 자리를 골랐다. 밑줄만
    한 글자 밀려 보인 이유다.
- **고침** : 글자도 **같은 스택으로 직접 그린다**(`drawGlyphs` / `drawBackground`).
  이제 글자·배경·밑줄 셋이 언제나 같은 줄바꿈을 본다.
- 같이 손본 것 두 가지 —
  - 그릴 때 쓰는 통(`NSTextContainer`)의 높이를 **무제한**으로. UILabel 이 잰 높이를
    주면 이 엔진이 한 줄 더 필요하다고 판단했을 때 그 줄이 잘린다.
  - `sizeThatFits(_:)` 를 **재정의**해 높이도 같은 엔진으로 재게 했다. 안 그러면
    줄 수가 하나 달라졌을 때 뷰가 짧아져 마지막 줄이 잘린다.

> 교훈 : **덧그리는 것(밑줄·형광펜)이 있으면 글자도 같은 엔진으로 그려야 한다.**
> 위치를 재는 쪽과 그리는 쪽이 다르면, 둘이 같은 답을 내는 동안에만 우연히 맞는다.

### 4-30. O/X 해설 다시 설계 — 리서치와 적용 계획 — 📝 계획 (코드 미착수)

**요청** — "어머니가 문제를 읽고 자신이 무엇을 골랐는지 몰라. 처음은 「한국 최초의
국가는 고구려, 신라, 백제는 맞아요」로 잘못 고르셨어요. 「한국 최초의 국가는
고조선이에요.」 이렇게 되길 원하는데 이게 맞는지 모르겠어. 리서치를 먼저 해주고
계획을 만들자." (선택: 사실 한 줄 붙이기 · 읽어주지 않기 · 맞혔을 때도 같은 형식)

**지금 무엇이 문제인가** — O/X 를 틀리면 배지가 「❌ 맞아요」로 뜬다. 어머니에게
「맞아요」는 **무엇에 대해** 맞다고 한 것인지가 사라진 낱말이다. 그 아래 문장 속
다른 낱말(예: 광복절) 설명, 「정답 보기」 뒤에 「✅ 삼일절」 + 모델 해설이 붙는다.
문장 → 내 판단 → 올바른 문장이 한 번도 **한 자리에** 나란히 놓이지 않는다.
관찰: 9/11 해설 뒤 자기가 고른 것을 잊음 · 9/14 「왜 틀렸지?」 · 9/14 5회차 오답
3개가 전부 O/X, 맞는 문장엔 「아니에요」, 틀린 문장엔 「맞아요」가 뒤섞임
(질문과 정답의 맥락을 아직 잇지 못한다는 가설).

**리서치에서 확인한 것**

| 연구 | 확인한 것 | 설계에 쓰는 방식 |
|---|---|---|
| Skurnik, Yoon, Park & Schwarz 2005 (J. Consumer Research) — 71~86세 | 「거짓」이라고 **세 번** 알려 준 주장을 3일 뒤 **40%** 가 참으로 기억(한 번은 28%). 젊은 층은 반대로 좋아짐. 권고: 거짓을 되풀이하기보다 **참인 것에 집중** | 틀린 문장은 **한 번만, 작게**, 「고르셨어요」라는 **어머니의 선택**으로만 보여 준다. 크게·마지막에 남는 것은 올바른 문장 |
| Swire, Ecker & Lewandowsky 2017 (JEP:LMC) — 50~87세 | 교정 직후엔 둘 다 효과, **1주 뒤 틀린 믿음이 되돌아옴**. 65세 이상에서 더 약함. 자세한 이유를 붙인 교정이 더 오래 감. 되풀이 교정 권장 | 「💡 사실 한 줄」로 **이유**를 붙인다. 같은 사실을 다음 회차에 다른 방식으로 다시 묻는다(19번 복습과 연결) |
| Pashler, Cepeda, Wixted & Rohrer 2005 (JEP:LMC) | 오답 뒤 **정답을 보여 주면** 1주 뒤 기억이 494% 늘었고, 「맞음/틀림」만 알려 주면 효과 없음 | 「❌ 맞아요」 배지(= 틀림 표시)만으로는 안 된다. **정답이 든 문장**을 보여 준다 |
| Butler, Karpicke & Roediger 2008 (JEP:LMC) | **확신 없이 맞힌** 답도 피드백이 있어야 오래 남는다 | 맞혀도 올바른 문장을 보여 준다(9/17 「애매하게 맞춘 것도 있었어」) |
| Brabec, Pan, Bjork & Bjork 2021 (Educ. Psych. Review) | 참 문장은 그 내용을, 거짓 문장은 **관련 내용**을 더 기억하게 한다. 문장 안에 경쟁하는 답을 넣으면(「A(B 아님)」) 둘 다 좋아짐 | 틀린 문장을 골랐을 때는 **바뀐 낱말만** 대비(~~고구려, 백제, 신라~~ → **고조선**) |
| Hildenbrand & Wiley 2025 (Memory & Cognition) | 이해 학습에는 **선다형이 O/X 보다 나음** — O/X 는 비교할 대안이 없어 깊이 생각하게 만들지 못함 | 틀린 O/X 뒤에 **둘 중 고르기** 한 번(2단계) |
| Cyr & Anderson 2012 (Psychonomic Bull. & Rev.) | 노년층도 **선다·소거처럼 받쳐 주는 형식**에서는 오류를 잘 고친다 | 같은 이유 |
| Arcos, Hausman & Storm 2024 (QJEP) | 참·거짓 판단은 공부보다 오래 걸리고(8.5초 vs 4.7~6.1초) 12분 지연 뒤 이득이 사라짐 | O/X 는 **확인용**으로 두고, 배우는 순간은 해설 창이 맡는다 |

**판단 — 제안하신 방향은 맞다. 두 가지만 조정한다.**
1. 어머니가 **무엇을 골랐는지**를 문장으로 되돌려 주는 것은 필요하다. 다만
   틀린 문장을 크게 다시 읽히면 노년층에서는 익숙함 때문에 오히려 참으로 남을 수
   있다(Skurnik). → 「고르셨어요」 줄은 **작게·회색·한 번**, 올바른 문장이 **크게·마지막**.
2. 틀린 것과 맞는 것을 **같은 자리에서 대비**하되(공간 근접), 되풀이하는 것은
   올바른 문장뿐이다.

**새 해설 — 네 경우** (모두 코드가 만든다. 모델 없음 · 기다림 없음 · 지어낼 일 없음)

```
① 틀린 문장에 「맞아요」 (가장 흔함)
   ❌ 「고구려, 백제, 신라」가 맞다고 고르셨어요        ← 작게·회색
   한국의 최초 국가 이름은 고조선이에요.               ← 크게, 고조선 녹색
   💡 기원전 2333년에 세워졌어요

② 맞는 문장에 「아니에요」
   ❌ 이 말은 맞는 말이었어요
   한국의 최초 국가 이름은 고조선이에요.
   💡 기원전 2333년에 세워졌어요

③ 틀린 문장에 「아니에요」 (맞힘)      ④ 맞는 문장에 「맞아요」 (맞힘)
   잘 맞추셨어요!                         잘 맞추셨어요!
   한국의 최초 국가 이름은 고조선이에요.   (같음)
   💡 …
```

- 올바른 문장 = `statementFormat` 에 `displayAnswer` 를 넣은 것. 끝의 「{답}이다.」를
  받침에 따라 「이에요 / 예요」로 바꾼다(고조선**이에요**, 태극기**예요**).
- 사실 한 줄 = `facts` 에서 `asks`(「나라 이름을 묻고 있어요」)를 **뺀** 것 중 weight 가
  가장 높은 하나. 50문항 모두 facts 가 있다.
- 박자 — O/X 는 **한 번에** 보여 준다. 두 박자로 나누면 「고르셨어요」와 올바른
  문장이 떨어져 9/11 처럼 고른 것을 잊는다. (「정답 보기」 버튼 없음)
- 읽어 주기 없음(선택하신 대로). 뒤 화면 잠금은 그대로.

### 4-31. O/X 해설 적용 — 누르면 바로 채점 · 빨간 펜 창 — ✅ 적용 (빌드 확인 필요)

**요청** — 데모 B(빨간 펜) 채택. 오답: 「다시 봐요」·「이 말은 맞는 말이었어요」 삭제,
「❌ 고르신 답」, 아래 FM 해설. 정답: 「맞았어요」 삭제, 「✅ 고르신 답」, 아래 FM 해설.
「고르신 답」 밑에 ✅ 를 두어 바른 문장임을 표시. 카드 안 글자는 **모두 바른 문장 크기(21)**.
맞아요/아니에요를 누르면 정답은 녹색, 오답은 붉은색 + 왼쪽 표시 ✕. 「다음」 없이 **누르면 바로** 창.

**흐름** — 누름 → 제출·채점(규칙) → 버튼 색(녹 ✓ / 분홍 ✕) → 0.6초 → 절반 창.
해설은 그 0.6초 동안 뒤에서 만들기 시작한다. 한 번 누르면 다시 못 고른다.

| `Session/QuizItem.swift` | `isTrueFalse` |
| `Grading/Commentary.swift` | `TrueFalseCommentary` (누른 라벨·맞았나·문장 참이었나·화면 낱말·정답·문장 앞뒤·해설) |
| `DesignSystem/CorrectionText.swift` (새) | 한 문장 안에 줄 그은 낱말 + 칠한 정답. 양쪽 정렬 규칙은 KoreanTextLayout 그대로 |

② 긴 지문(제헌절)에서 버튼이 창 위로 보이는지, 글자가 너무 작아지지 않는지(최소 20pt)
③ 21pt 로 맞추면서 긴 문장 + 해설이면 카드가 스크롤된다 — 괜찮은지

### 4-32. O/X 판단 낱말의 큰따옴표 → 낫표(「 」) — ✅ 적용 (빌드 확인 필요)

**요청** — 데모의 「고구려, 백제, 신라」 모양이 예쁘다, 지문의 " " 를 바꿔 달라.

- `KoreanText.swift` — `“답”` → `「⁠답⁠」`. 낫표와 낱말 사이에 WORD JOINER(U+2060)를 넣어
  「 만 줄 끝에 남거나 」 만 다음 줄로 떨어지지 않게 붙였다. 색(시그니처)·굵기(.heavy)는 그대로.
- `QuestionScreen.swift` — 지문 글자 크기를 잴 때도 낫표를 붙여 잰다. 낫표가 따옴표보다
  넓어서, 안 붙이고 재면 한 줄 모자라게 재 지문이 절반 선을 넘을 수 있다.

> 막혀 있어 git 이 잠금 파일을 못 지웠다). `_to_delete/git-index.lock.stale` 로 옮겨 두었다.

### 4-33. CommentaryWriter 의 write · describe 를 explain 하나로 — ✅ 적용 (빌드 확인 필요)

**왜** — 둘 다 「문항 하나의 facts 로 그 답을 설명한다」는 같은 일이고, 재료 고르기
(`materials(for:)`)와 모델 부르기(`ModelCall.generate`)도 같았다. 다른 것은 길이와 지시문뿐.

- 바깥 입구는 `explain(_ question: Question?, length: .full | .oneLine)` 하나.
  `.full` = 예전 `write(for:)`(정답 50~60자), `.oneLine` = 예전 `describe(_:)`(고른 오답 한 문장).
- `nil` 문항·재료 없음 처리가 입구 한 곳으로 모였다.
- **지시문·프롬프트 문장, 로그의 job 이름(`commentary`·`note`)은 한 글자도 안 바꿨다** — 동작 변경 없음.
- 부르는 곳 4군데(`QuizSession` 570·617·683·684)와 문서 주석·DocC 링크를 새 이름으로 고쳤다.
- 참고: `tone(for:)` 는 지금 아무도 부르지 않는다(지시문에서 말투 줄이 빠져 있음). 지우지 않았다.

**다음(미결)** — 4-30 후속으로 찾은 해설 품질 문제: asks 가 재료에 섞임, 50문항 중 47문항은
진짜 사실이 50자 미만인데 50자 이상을 강제 → 빈말·답 되풀이. `explain` 한 곳만 고치면 된다.

### 4-34. questions.json 의 asks 50개 → 사실 한 줄로 교체 — ✅ 적용

**요청** — 「나라 이름을 묻고 있어요」 같은 문장이 프롬프트에 들어가 해설을 망친다. 다른 사실로 바꿔 달라.

- 50문항의 `asks`(무게 3)를 **그 답에 대한 사실 한 줄**(대부분 `mark`·무게 2)로 바꿨다. 다른 칸은 한 글자도 안 바뀌었다(스크립트로 대조).
- 왕인 세종대왕만 규칙 ②대로 `nation`·무게 3 — 「조선의 네 번째 임금이에요」.
- 규칙을 지켰다 — 질문에 있는 말은 피하고(국경일 사건은 예외), 헷갈리는 다른 답을 끌어오지 않고, 쉬운 말로.

- `해설_재료_규칙.md` 의 asks 규칙을 폐지로 고쳤다.

**남은 것** — ① 50자 이상 강제는 그대로라, 재료가 여전히 짧은 문항은 빈말이 나올 수 있다.

`wordplay` 로 잘못 붙어 있다(글자 뜻이 아님).

### 4-36. 초기화 뒤 새 문제가 안 나오던 것 — 신규 도입 순서 고침 — ✅ 적용 (빌드 확인 필요)

**증상** — 기록을 초기화해도 50문항이 고르게 안 나오고, 11차에 새로 넣은 문항(인물·정치·음식)이 안 보인다.

**원인** — `SessionBuilder.introduceOrder` 는 신규를 단원별로 번갈아(라운드로빈) 세우는데,
① 이 줄이 **회차마다 새로** 세워지고 ② 회차에 신규는 **2칸**뿐이라, 매번 맨 앞 두 단원
(역사1·국경일)에서만 꺼냈다. 그 두 단원이 바닥날 때까지 다른 단원은 차례가 오지 않았다.
초기화 뒤 흉내(전부 맞힌다고 가정): 정치 39~45 는 11~23회차, 음식 46~50 은 13~17회차에야 처음 등장.

**고침** — 라운드로빈을 **이미 나온 문항이 적은 단원부터** 시작한다(`introducedByUnit`).
같은 흉내에서 모든 단원의 첫 문제가 1~2회차, 그 뒤 단원마다 서너 회차에 하나씩.
전체가 한 번씩 나오는 데는 여전히 약 23회차 — 신규 2칸이 정한다. 더 빨리 돌리려면 `newcomerSlots` 를 3으로.

### 4-37. 복습 모드 — 결과 전에 틀린 문제 한 번 더 — ✅ 적용 (빌드 확인 필요)

**요청** — 틀린 문제를 결과 화면 전에 다시 묻는다. 시안 A(같은 화면 + 복습 띠) 채택 — 해설 창도 재활용.
결과: 다시 풀어서 정답은 **노랑**, 모든 줄에 정답 표기, 「처음엔 놓쳤지만…」 문구 없음, 복습에서도 틀리면 「틀렸어요」.

**흐름** — 마지막 칸 → (틀린 게 있으면) 복습 시작 화면 「틀린 N문제만 한 번 더 볼게요」 → 복습 문제들
(본 문제 화면 그대로, 맨 위만 연보라 띠 + 「복습 1 / N」 + 복습 진행 막대) → 채점 중 3초 → 결과.
틀린 게 없으면 복습 없이 곧바로 결과.

| 파일 | 바뀐 것 |
|---|---|
| `Screens/QuizSession.swift` | `reviewItems`·`reviewIndex`·`isShowingReviewIntro`·`isInReview`·`reviewResults`·`startReview()`·`reviewOutcome(for:)`. `current` 가 복습 중엔 복습 문항을 준다. `moveToNextQuestion` 이 복습 안에서 넘기고, 본 풀이가 끝나면 틀린 게 있을 때 복습 시작 화면으로 |
| `Screens/ReviewIntroScreen.swift` (새) | 복습 시작 화면 |
| `Screens/QuizView.swift` | 다 푼 뒤 갈래: 복습 시작 → 복습 문제(QuestionScreen) → 채점 중 → 결과. 읽어 주기는 칸 번호 대신 문항이 바뀔 때 |
| `Screens/QuestionScreen.swift` | 복습 중 머리 줄(띠·알약·진행 막대). 띠 두께만큼 지문 몫에서 뺀다 |
| `Screens/ResultScreen.swift` | 세 칸: 정답(녹색 ✓) · 다시 풀어서 정답(노랑 ↻) · 틀렸어요(분홍 ✕). 모든 줄에 「정답: …」 |
| `DesignSystem/AppColor.swift` | `reviewCorrect`(짙은 노랑, 글자·아이콘) · `reviewCorrectBackground`(옅은 노랑, 줄 배경) |

**정해서 넣은 것 (바꿀 수 있음)**
- 복습 문제는 **본 풀이와 같은 방식·같은 보기**로 다시 묻는다. 해설 창도 본 풀이와 같다(O/X 창 포함).
- 복습 결과는 **맞힌 개수(누적)에는 세고, 난이도 사다리는 안 움직인다** — 방금 정답을 본 직후라.
- 본 풀이 결과(`results`)는 복습이 덮어쓰지 않는다. 결과 화면 「오늘 N문제 중 M개」도 본 풀이 기준.
- **복습 풀이는 `obs_record` 에 안 남긴다** — 「복습이었나」 칸이 없어 섞이면 본 풀이 통계가 흐려진다. 남기려면 Supabase 에 칸(예: `is_review`)부터.
- 안내 문구는 문항의 원래 것(「이 말이 맞을까요?」 등)을 그대로 쓴다 — 시안의 「한 번 더 풀어 볼까요?」 대신. 무엇을 할지가 사라지지 않게.

**확인할 것** — ① 틀린 게 0개면 복습 없이 결과 ② O/X·선다·직접입력 복습에서 해설 창이 뜨고 「다음」으로 넘어가는지
③ 결과 화면 세 칸 색 ④ 노랑(다시 풀어서 정답)과 주황(완전히 익힘 별)이 헷갈리지 않는지 ⑤ 복습 첫 문제를 읽어 주는지
