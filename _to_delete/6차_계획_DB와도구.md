# 6차 계획 — 문제 DB 와 도구(tool)

> 2026-09-08. 문제집을 JSON 에서 데이터베이스로 옮기고, 힌트는 모델이 **DB 에서 재료를 꺼내 조합**하게 한다.
> 정답 체크를 먼저 손보고, 힌트는 그다음이다.

---

## 0. 먼저 갈라야 할 것 — 무엇을 모델에게 시키고, 무엇을 안 시키나

지금까지 겪은 사고가 전부 **모델에게 안 시켜야 할 것을 시켜서** 났다.

| | 모델이 잘하는 것 | 모델이 못하는 것 |
|---|---|---|
| | 주어진 재료를 **말로 다듬기** | 사실을 **기억해 내기** (제헌절 10월 3일) |
| | 문장의 모양 따라 하기 | **정확한 비교** (고죠선 = 고조선) |
| | 여러 재료를 **엮기** | 자기가 아는지 모르는지 판단하기 |

그래서 이렇게 나눈다.

```
정답 체크   글자 비교는 코드가 · 모델은 「군더더기 걷어내기」만
힌트        사실은 DB 가 · 모델은 「조합하고 말로 풀기」만
```

**두 곳 다 모델에게 사실을 묻지 않는다.**

---

## 1. 정답 체크에 tool 을 쓰지 않는 이유

tool calling 은 **모델이 필요하다고 판단하면 부르는** 구조다. 부를지 말지를 모델이 정한다.

채점은 **결정적**이어야 한다. 같은 답을 두 번 내면 두 번 다 같게 나와야 한다. 「모델이 도구를 부를 수도 있고 안 부를 수도 있는」 구조는 채점에 맞지 않는다.

그리고 **채점에 필요한 정답을 우리는 이미 알고 있다.** 문항을 우리가 골라서 냈기 때문이다. 도구로 꺼내 올 이유가 없다 — 프롬프트에 넣으면 된다.

> **tool 이 값어치 있는 자리는 힌트다.** 「이 문항에 무슨 재료가 있지?」를 모델이 스스로 찾아야 하고, 어머니가 「더 알려줘」 하면 **또 찾아야** 하기 때문이다. 그때는 몇 번 부를지 미리 알 수 없다 — 그게 tool 이 필요한 상황이다.

## 2. 문제 DB — SwiftData 로 만든다

### 지금 구조

```
Content/questions.json  →  QuestionCatalog(번들에서 읽음)  →  SessionBuilder
```

문항이 20개일 때는 이걸로 충분했다. 1,130개가 되고 힌트 재료까지 붙으면 **JSON 한 덩어리를 통째로 메모리에 올리는 것**이 부담이 되고, 무엇보다 **검색이 안 된다.**

### 세 가지 길

| | 어떻게 | 배포 | 문항 늘리기 | 검색 |
|---|---|---|---|---|
| **ⓐ JSON 그대로** | 지금 | 앱에 포함 | 앱 업데이트 필요 | 메모리에서 훑기 |
| **ⓑ SwiftData + 첫 실행에 적재** | JSON 을 번들에 두고 처음 켤 때 DB 로 옮긴다 | 앱에 포함 | 앱 업데이트, **나중에 서버에서 받기 가능** | 쿼리 |
| **ⓒ Supabase 에서 받기** | 서버가 원본 | 앱은 빈 채로 | 앱 업데이트 없이 | 쿼리 |

**ⓑ 로 간다.** 이유 셋.

1. **배포에 문제가 없다.** 번들 JSON 은 앱과 함께 나가고, 첫 실행에서 SwiftData 로 옮긴다. 인터넷이 없어도 된다
2. **이미 SwiftData 를 쓰고 있다.** `QuestionProgress`·`ObsRecord`·`QuestionFocusRecord` 가 같은 저장소에 있다. 문항이 같은 곳에 있으면 **진척과 문항을 한 번의 쿼리로 이을 수 있다**
3. **나중에 ⓒ 로 갈 수 있다.** 적재하는 곳만 바꾸면 된다 — 번들 JSON 대신 Supabase 에서 받아 같은 테이블에 넣는다. 그러면 **앱 업데이트 없이 문항을 늘릴 수 있다**

> **ⓒ 를 지금 하지 않는 이유** — 문제를 푸는 데 인터넷이 필요해지면 안 된다. 어머니가 지하철에서도 푸실 수 있어야 한다.

### 새 모델 둘

```swift
@Model
final class StoredQuestion {
    @Attribute(.unique) var id: Int
    var category: String
    var unit: String
    var question: String
    var answer: String
    var kindRaw: String          // AnswerKind
    var statementFormat: String
    var difficulty: Int
    ...
}

@Model
final class QuestionFact {
    var questionID: Int
    var kindRaw: String          // 재료의 종류 (아래 표)
    var text: String             // 재료 한 조각
    var weight: Int              // 힌트에 먼저 쓸 순서
}
```

**`QuestionFact` 가 이 계획의 심장이다.** 힌트에 쓸 재료를 조각으로 나눠 둔다. 모델은 이 조각들을 **조합만** 한다.

| 재료 종류 | 예 (q12 제헌절) |
|---|---|
| `date` | 7월 17일 |
| `year` | 1948년 |
| `event` | 대한민국 헌법을 만들어 알린 날 |
| `wordplay` | '헌'은 헌법의 헌 |
| `pairsWith` | 헌법 · 국경일 |
| `confusedWith` | 개천절(10월 3일)과 헷갈리기 쉽다 |
| `everyday` | 나라의 법이 생긴 날이라 관공서가 쉰다 |

**한 문항에 조각이 여럿**이고, 모델은 그중 **두세 개를 골라** 문장으로 만든다. 그래서 같은 문항이라도 **매번 다른 해설**이 나오면서 **사실은 늘 같다.** 형님이 원하던 「고정 힌트는 싫고 매번 다르게」가 여기서 풀린다.

`confusedWith` 는 어머니의 로그에서 나온 것이다 — 나라와 국경일을 섞으신다. **그 문항에만 붙는 재료**다.

### 적재는 이렇게

```swift
// QuestionStore.seedIfNeeded()
// 1. 저장된 문제집 버전을 읽는다 (UserDefaults 나 별도 @Model)
// 2. 번들 JSON 의 version 과 같으면 아무것도 안 한다
// 3. 다르면 StoredQuestion·QuestionFact 를 전부 지우고 다시 넣는다
```

**진척(`QuestionProgress`)은 건드리지 않는다.** 문항 id 로만 이어져 있으므로, 문제집을 갈아 끼워도 어머니의 사다리는 그대로 남는다. **id 는 절대 재사용하지 않는다** — 이미 `Question.swift` 주석에 적어 둔 규칙이다.

## 3. 정답 체크 — 어떻게 구성하나

### 큰 그림

```
답 제출
  ↓
① RuleGrader        선다·O/X → 즉시 판정 (지금 그대로)
  ↓ nil (직접입력)
② TextNormalizer    군더더기·공백·문장부호를 코드가 지운다   ← 새로 만든다
  ↓ 글자가 같은가?
  ├ 같다   → 정답. 모델을 안 부른다
  └ 다르다 → ③ 모델에게 한 번만 물어본다
```

**②가 핵심이다.** 지금 「고죠선」이 통과한 것도, 17.9초가 걸리는 것도, 안전 필터에 걸리는 것도 **모델을 부르기 때문**이다. 대부분의 정답은 코드로 즉시 갈린다.

모델은 **②에서 안 걸러진 것만** 본다. 「음 이건 고조선인 것 같은데요」처럼 군더더기가 우리 목록에 없는 경우다.

### ③ 의 `@Generable` — 형님 안을 조금 고친 것

형님 안은 이랬다 — 정답 이유 string, 오답 이유 string, bool, 퀴즈 id string.

**두 군데를 고치자고 제안한다.**

```swift
@Generable
struct AnswerCheck {
    @Guide(description: "군더더기를 걷어낸 뒤 정답과 글자가 모두 같으면 true. 한 글자라도 다르면 false")
    let isCorrect: Bool

    @Guide(description: "어떻게 판정했는지 한국어 한 문장. 글자가 다르면 어느 글자가 다른지 적는다")
    let reason: String

    @Guide(description: "판정의 근거")
    let basis: CheckBasis
}

@Generable
enum CheckBasis {
    case exactMatch        // 글자가 그대로 같다
    case afterTrimming     // 군더더기를 걷어내니 같다
    case differentLetters  // 한 글자 이상 다르다
    case differentName     // 아예 다른 이름이다
    case undecided         // 답을 둘 이상 대고 정하지 않았다
    case partialList       // 여러 항목 중 일부만 말했다
}
```

**① 이유를 하나로 합친다.** 「정답 이유」와 「오답 이유」를 나누면 모델이 **둘 다 채우려 하고**, 안 쓰는 쪽에 헛소리가 들어간다. `isCorrect` 가 이미 방향을 정하므로 이유는 하나면 된다.

**② 퀴즈 id 를 모델에게 만들게 하지 않는다.** id 는 **우리가 이미 알고 있다.** 모델에게 시키면 **바꿔 적을 위험**만 생긴다 — 「'안'은 옛날이라는 뜻」을 지어낸 그 모델이다. **모델은 자기가 아는 것만 만들게 한다.** id 는 코드가 붙인다.

**③ 대신 `basis` 를 넣는다.** 이게 형님이 원하던 것보다 낫다 — 로그에 「어떤 이유로 통과시켰나」가 **낱말이 아니라 값으로** 남으므로, 나중에 이렇게 셀 수 있다.

```sql
select basis, count(*) from obs_record where mode_raw = 3 group by basis;
```

`afterTrimming` 이 많으면 ②의 군더더기 목록을 늘리면 되고, `differentLetters` 인데 정답 처리된 줄이 있으면 **모델이 규칙을 어긴 것**이 바로 잡힌다.

### instructions — 10단계에서 쓴 것을 그대로

`5차_구현.md` 10단계의 절차형 지침을 쓴다. 다만 ② 가 앞에서 걸러 주므로 **더 짧아져도 된다.**

```
당신은 한국어 받아쓰기 채점기입니다.
'정답'과 '답변'의 글자가 같은지만 봅니다. 뜻이나 소리가 비슷한지는 보지 않습니다.

[절차]
1단계. 답변에서 앞뒤 군더더기를 지웁니다.
2단계. 남은 글자를 정답과 앞에서부터 맞춰 봅니다.
3단계. 모두 같으면 정답, 하나라도 다르면 오답입니다.

[오답으로 두는 것]
· 글자가 하나라도 다르다. 소리가 비슷해도 오답이다.  "고죠선" · "태국기"
· 글자가 빠졌거나 더 붙었다.                        "조선" · "세종"
· 다른 이름이다.                                    "단군신화"
· 답을 둘 이상 대고 정하지 않았다.
· 여러 항목 중 일부만 말했다.

확실하지 않으면 오답으로 둡니다.
```

### prompt

```
정답: 고조선
답변: 음 이건 고조선인 것 같은데요

답변이 정답과 같은지 채점하세요.
```

**문제 지문을 넣지 않는다.** 이유 둘 — 채점에 필요 없고(글자만 보면 된다), **지문의 「일제의 지배」·「목숨을 바친」 같은 낱말이 안전 필터에 걸린다.** 9/6 에 `May contain unsafe content` 가 났던 그 자리다.

### `GenerationOptions`

```swift
try await session.respond(
    to: prompt,
    generating: AnswerCheck.self,
    options: GenerationOptions(temperature: 0.1)
)
```

**채점은 온도를 낮춘다.** 같은 답이 같게 채점되어야 한다. 지금은 기본값이라 회차마다 흔들릴 수 있다 — 「테국기」가 한 번은 통과하고 한 번은 안 된 것이 이것일 수 있다.

## 4. 힌트 — 여기서 tool 을 쓴다

### tool 하나면 된다

```swift
struct QuestionFactTool: Tool {
    let name = "문항재료찾기"
    let description = "문항 번호로 그 문항의 사실 재료를 찾아 줍니다. 날짜, 있었던 일, 글자 뜻, 헷갈리기 쉬운 것 등입니다."

    @Generable
    struct Arguments {
        @Guide(description: "문항 번호")
        let questionID: Int
    }

    func call(arguments: Arguments) async throws -> String {
        // SwiftData 에서 QuestionFact 를 읽어 줄글로 만들어 돌려준다
    }
}
```

세션을 만들 때 붙인다.

```swift
let session = LanguageModelSession(
    tools: [QuestionFactTool(modelContext: modelContext)],
    instructions: instructions
)
```

### 왜 프롬프트에 재료를 그냥 넣지 않고 tool 로 하나

**한 번만 보여줄 거면 프롬프트에 넣는 편이 낫다.** tool 은 **여러 번, 그때그때** 필요할 때 값어치가 있다.

```
어머니 : (오답) → 힌트가 뜬다
어머니 : "왜 그런데?"          → 모델이 같은 문항의 다른 재료를 또 꺼낸다
어머니 : "개천절이랑 뭐가 달라?" → confusedWith 재료를 꺼내고, 개천절 문항의 재료도 꺼낸다
```

**대화형으로 가면 무엇이 필요할지 미리 알 수 없다.** 그때 tool 이 필요하다. 형님이 그리신 그림이 정확히 이것이다.

### 힌트의 `@Generable`

```swift
@Generable
struct Hint {
    @Guide(description: "어르신에게 건네는 두 문장 이내의 설명. 재료에 있는 것만 쓴다")
    let text: String

    @Guide(description: "이 설명에 쓴 재료의 종류", .maximumCount(3))
    let usedFacts: [String]
}
```

`usedFacts` 를 받는 이유 — **모델이 재료를 안 쓰고 지어냈는지** 알 수 있다. 비어 있으면 도구를 안 부른 것이다. 로그에 남기면 **환각이 다시 새는 순간을 숫자로** 잡는다.

### 대화를 이어갈 때 — 문서 4번(context window)

- **채점은 매번 새 세션.** 문항끼리 독립이라 앞의 대화가 남으면 방해만 된다
- **힌트는 세션을 이어간다.** 「왜?」에 답하려면 앞의 이야기를 알아야 한다
- 다만 창(context)은 무한하지 않다. 대화가 길어지면 `LanguageModelSession(transcript:)` 로 **앞부분을 잘라내고 요약만 남겨** 새 세션을 만든다. 문서 4번의 방식 그대로다
- 실제로는 **한 문항의 대화가 서너 번을 넘지 않을 것**이라 당분간 걱정할 일은 아니다. 넘치는지 확인만 해 둔다

## 5. 순서

```
1. TextNormalizer          코드로 걸러내기. 모델을 부르는 횟수가 확 준다
2. AnswerCheck             @Generable 을 basis 까지 넓히고 temperature 0.1
3. StoredQuestion 적재     JSON → SwiftData. 동작은 그대로여야 한다
4. QuestionFact 스키마     재료 종류를 정하고 20문항에 채운다
5. QuestionFactTool        tool 하나. 힌트가 재료를 쓰게 된다
6. 대화형                  「왜?」에 답하기. 세션 이어가기
```

**1·2 는 지금 겪는 문제를 바로 고친다.** 3~6 은 힌트를 위한 바닥 공사다.

**3 번에서 조심할 것** — 적재를 넣어도 `SessionBuilder`·`QuestionCatalog` 가 보는 결과는 **똑같아야 한다.** 문제집을 옮기는 일과 힌트를 바꾸는 일을 같은 단계에 넣으면, 무엇이 깨졌는지 알 수 없게 된다.

## 6. 더 쓸 수 있는 것들

문서 넷을 읽고 지금 앱에 바로 값어치가 있어 보이는 것들이다.

| 무엇 | 어디에 쓰나 | 왜 |
|---|---|---|
| **`prewarm()`** | 회차를 시작할 때 미리 부른다 | 첫 직접입력의 기다림이 줄어든다. 지금 중앙 17.9초의 일부가 **모델을 깨우는 시간**이다 |
| **`streamResponse`** | 힌트를 글자가 흐르듯 보여준다 | 「잠시만 같이 살펴봐요.」로 3초를 버티는 대신 **첫 글자가 0.5초에 나온다.** 기다림이 짧게 느껴진다 |
| **`SystemLanguageModel.availability`** | 앱을 켤 때 한 번 | 모델을 못 쓰는 기기인지 미리 안다. 지금은 실패한 뒤에야 안다 |
| **`@Guide(.anyOf([...]))`** | 유형·재료 종류처럼 값이 정해진 자리 | 모델이 없는 값을 지어낼 수 없게 된다 |
| **`temperature`** | 채점은 낮게, 힌트는 조금 높게 | 채점은 흔들리면 안 되고, 힌트는 매번 달라야 한다 |
| **`Transcript`** | 대화형 힌트 | 앞 이야기를 이어가되 길어지면 요약으로 갈아 끼운다 |

**가장 먼저 넣을 만한 것은 `prewarm()` 과 `streamResponse` 다.** 둘 다 코드가 적고, 어머니가 **바로 느끼는 것**을 고친다.
