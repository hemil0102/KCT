# 5차 구현 — 여섯 단계

> 단계마다 빌드해서 확인할 수 있게 갈라 두었다. **순서대로 간다.**
> 1~4 는 지금 바로, 5 는 entitlement 승인 뒤, 6 은 5 와 짝이다.

| 단계 | 무엇 | 파일 | 빌드하면 보이는 것 |
|---|---|---|---|
| **1** | 직접입력도 다른 문항과 똑같이 | `QuizView` · `QuestionScreen` · `GradingScreen` | 채점 화면이 안 끼어든다 |
| **2** | 채점 뒤 낭독이 안 되는 것 | `QuizView` | 다음 문제를 읽어 준다 |
| **3** | 「테국기」가 정답이 되는 것 | `MeaningGrader` | 오채점이 줄어든다 |
| **4** | 「잠시만 같이 살펴봐요.」에 움직임 | `FeedbackSheet` | 기다리는 중임이 보인다 |
| **5** | PCC 적용 | Supabase · `CommentaryWriter` · 로그 3파일 | 해설이 정교해진다 |
| **6** | 온디바이스 경로를 남긴다 | `CommentaryWriter` · 개발용 스위치 | 둘을 번갈아 비교할 수 있다 |

# 1단계 — 직접입력도 다른 문항과 똑같이

## 왜

지금은 직접입력일 때만 화면이 이렇게 바뀐다.

```
QuestionScreen  →  GradingScreen(「채점 중이에요」)  →  QuestionScreen
```

어머니에게는 **문제가 사라졌다가 다시 나타나는 것**이다. 9/5 에 「문제가 나온 게 아닌가」 하고 헷갈리신 자리다. 선다·O/X 는 이런 일이 없다.

**화면을 바꾸지 않고, 버튼만 바꾼다.** 문제는 그대로 있고 「채점 중이에요」가 버튼 자리에 뜬다. 그러면 2단계의 낭독 문제도 뿌리가 같이 사라진다 — 화면이 안 없어지니 감시자도 안 없어진다.

## ① `KCT/Screens/QuizView.swift` — `screen(for:)` 에서 채점 분기를 뺀다

```swift
    @ViewBuilder
    private func screen(for session: QuizSession) -> some View {
        if session.isFinished {
            ResultScreen(
                session: session,
                onRestart: { restart(session) },
                onEraseProgress: { erase(session) }
            )
        } else {
            QuestionScreen(session: session, sessionMode: sessionMode) {
                readAloud(session.current)
            }
            // 문제가 넘어가면 새 지문을 자동으로 읽어준다.
            .onChange(of: session.currentIndex) { _, _ in
                readAloud(session.current)
            }
        }
    }
```

`if session.isGrading { GradingScreen() } else if …` 였던 것을 `if session.isFinished { … } else { … }` 로 되돌린 것이다. **`.onChange` 는 일단 그대로 둔다** — 2단계에서 옮긴다.

## ② `KCT/Screens/QuestionScreen.swift` — `nextButton` 이 채점 중을 알린다

```swift
    private var nextButton: some View {
        PrimaryActionButton(
            title: session.isGrading
                ? "채점 중이에요"
                : (session.isLastQuestion ? "제출" : "다음  →"),
            isReady: session.hasAnswer && !session.isGrading
        ) {
            if session.isGrading { return }

            if session.hasAnswer {
                session.submitCurrent()
            } else {
                showAnswerHint()
            }
        }
    }
```

- **`isReady` 가 겉모습만 바꾼다.** 그래서 눌리는 것 자체는 첫 줄의 `return` 이 막는다
- 실제 이중 제출은 `submitCurrent()` 의 `guard !isGrading` 이 이미 막고 있다. 여기 것은 **어머니에게 보이는 쪽**이다

### 왜 직접입력만 버튼이 바뀌나 — 2026-09-06 결정

「모달이 먼저 뜨고 다른 문항과 똑같이 보이게」를 검토했지만 **그렇게 할 수 없다.**

```
선다·O/X   답 제출 → 즉시 판정 → 틀렸다 → 모달      기다림이 모달 안에 있다
직접입력   답 제출 → 1~3초 판정 → 틀렸다 → 모달      기다림이 모달 앞에 있다
```

모달은 **틀렸을 때만** 뜨는데, 직접입력은 틀렸는지를 알려면 기다려야 한다. 먼저 띄우려면 맞혔을 때도 띄웠다가 닫아야 하고, 그건 더 헷갈린다.

검토한 대안 둘 — **ⓐ 버튼 문구를 안 바꾸고 그냥 무반응으로 두기**(겉모습은 같아지지만 8/26 의 「눌러도 아무 일이 없으면 고장 난 줄 안다」에 걸린다), **ⓑ 채점과 해설을 동시에 출발시켜 기다림을 한 번으로 줄이기**(맞혔을 때도 해설을 만들어 헛일이 생기고 PCC 하루 한도를 더 쓴다).

**둘 다 안 하고 지금대로 간다.** 어머니가 실제로 이 버튼을 어떻게 겪는지 먼저 보고 정한다.

## ③ `KCT/Screens/GradingScreen.swift` — 아무도 안 부르게 된다

파일은 지우지 않는다. 파일 맨 위 주석에 **한 줄만** 더한다. (이건 내가 한다)

```
//  ⚠️ 2026-09-06 부터 아무도 부르지 않습니다.
//     채점 중임은 QuestionScreen 의 버튼이 알립니다.
```

## 확인

- **직접입력을 낸다** → 문제가 그대로 있고 버튼만 「채점 중이에요」로 바뀌는가
- 그동안 **버튼을 여러 번 눌러도** 아무 일이 없는가
- 선다·O/X 는 버튼이 안 바뀌는가 (판정이 즉시라 눈에 안 띈다)

# 2단계 — 채점 뒤에 문제를 읽어 준다

## 왜

낭독 감시자가 `QuestionScreen` **안에** 붙어 있다. 1단계로 화면이 안 갈아끼워지게 됐으니 증상은 이미 사라졌겠지만, **감시자를 화면 안에 두는 것 자체가 위험**하다. 나중에 화면이 하나 더 끼어들면 같은 일이 다시 난다.

## `KCT/Screens/QuizView.swift` — 감시자를 바깥으로

**ⓐ `screen(for:)` 의 `.onChange` 세 줄을 지운다**

```swift
            QuestionScreen(session: session, sessionMode: sessionMode) {
                readAloud(session.current)
            }
        }
    }
```

**ⓑ `body` 의 `.sheet` **위**에 붙인다**

```swift
        .onChange(of: session?.currentIndex) { _, _ in
            readAloud(session?.current)
        }
```

- `session` 이 옵셔널이라 `session?.currentIndex` 로 본다
- 회차가 끝나면 `current` 가 `nil` 이라 `readAloud` 가 스스로 아무것도 안 한다. 안쪽에 두었던 이유(「끝난 뒤엔 안 울리게」)는 그대로 지켜진다
- 모달이 떠 있는 동안에는 `currentIndex` 가 안 바뀐다. 「다음 문제」를 눌러 넘어갈 때 한 번 울린다

## 확인

- **직접입력을 틀린다** → 모달을 닫으면 다음 문제를 읽어 주는가
- **직접입력을 맞힌다** → 바로 다음 문제를 읽어 주는가
- **회차가 끝난다** → 결과 화면에서 아무 소리도 안 나는가

# 3단계 — 「테국기」가 정답이 되는 것

## 왜

`RuleGrader` 는 선다·O/X 를 정확히 같은지로만 본다. 그러니 이건 직접입력이고, `MeaningGrader`(온디바이스 모델)가 통과시킨 것이다.

지금 지침의 통과 규칙 2 가 「띄어쓰기만 다르다」인데, 모델이 이걸 **「비슷하면 통과」로 넓혔다.**

> 9/5 로그에서는 이미 정확히 오답으로 잡혔다 — *「정답은 태극기인데 답변은 태국기로 다른 이름이므로 오답입니다」*. 그래도 **못 박아 둔다.** 지금 안 잡히는 게 아니라 **때때로 안 잡히는 것**이 더 나쁘다.

## `KCT/Grading/MeaningGrader.swift` — 규칙 둘을 손본다

**ⓐ 통과 규칙 2 를 좁힌다**

```
                    2. 띄어쓰기나 문장부호만 다르다. 글자는 같아야 한다.
                       정답 "단군왕검" / 답변 "단군 왕검" → 정답
```

**ⓑ 오답 규칙 4 에 예시를 하나 더 붙인다**

```
                    4. 답변이 정답과 다른 이름이다.
                       글자가 겹치거나 같은 이야기에 나와도 다른 이름이면 오답이다.
                       한 글자라도 다르면 다른 이름이다.
                       정답 "단군왕검" / 답변 "단군신화" → 오답
                       정답 "태극기" / 답변 "태국기" → 오답
                       정답 "고조선" / 답변 "조선" → 오답
```

- **「한 글자라도 다르면」** 이 한 줄이 핵심이다. 「띄어쓰기만」이라는 좁은 예외를 남기고 나머지를 다 막는다
- 「조선」 예시는 8/31 에 실제로 있었던 판정이다. 그때는 맞게 잡혔는데, **맞게 잡힌 것도 예시로 남겨야** 흔들리지 않는다

## 생각해 둘 것 — 이게 정말 맞나

귀화 면접은 **말로** 본다. 어머니가 「태극기」라고 말하면 맞다. 앱에서는 손으로 치니 오타가 난다.

그래도 **오답 쪽으로 두는 것이 낫다.** 8/31 에 정한 원칙이 여기서도 통한다 — **틀렸는데 맞다고 하면 사다리가 잘못 올라가고 아무도 모르지만, 맞았는데 틀렸다고 하면 그 문항을 곧 다시 만나 스스로 회복된다.**

다만 나중에 **음성 입력**을 넣으면 이 판단을 다시 해야 한다. 그때는 오타가 아니라 인식 오류라 성격이 다르다.

## 확인

직접입력이 나오는 문항에서 일부러 한 글자를 틀린다.

```sql
select question_id, chosen, is_correct, reason
from obs_record
where mode_raw = 3
order by id desc limit 20;
```

`reason` 에 「다른 이름」이라고 적혀 있으면 규칙 4 가 작동한 것이다.

# 4단계 — 기다리는 중임을 보이게

## 왜

해설을 만드는 1~3초 동안 창에 「잠시만 같이 살펴봐요.」가 **가만히** 떠 있다. 어머니는 이게 **최종 문구인지 기다리는 중인지 모른다.** 실패해서 영영 안 바뀔 수도 있으니 더 그렇다.

**글자가 은은하게 밝아졌다 어두워지게** 한다. 점 세 개가 흐르는 것보다 덜 산만하고, 정답을 읽는 눈을 뺏지 않는다.

## `KCT/Screens/FeedbackSheet.swift`

**ⓐ 프로퍼티 둘을 더한다** — `let onNext` 아래

```swift
    /// 해설을 기다리는 동안 글자를 맥동시킨다.
    @State private var isPulsing = false

    /// 기기에서 「동작 줄이기」를 켠 분에게는 맥동을 끈다.
    @Environment(\.accessibilityReduceMotion) private var reduceMotion
```

**ⓑ 해설 `Text` 의 `.opacity` 한 줄을 교체**

```swift
                    .opacity(commentaryOpacity)
```

**ⓒ `body` 의 `.interactiveDismissDisabled()` 아래에 두 줄**

```swift
        .animation(pulseAnimation, value: isPulsing)
        .onAppear { isPulsing = true }
```

**ⓓ `commentaryText` 아래에 계산 프로퍼티 둘**

```swift
    /// 해설 글자의 진하기. 준비 중이면 옅게, 도착하면 또렷하게.
    ///
    /// 「동작 줄이기」를 켰거나 해설이 도착했으면 고정 값이라 맥동이 멈춥니다.
    private var commentaryOpacity: Double {
        if feedback.isReady { return 1 }
        if reduceMotion { return 0.45 }
        return isPulsing ? 0.6 : 0.25
    }

    /// 맥동용 애니메이션. 준비 중일 때만 돌고, 도착하면 `nil` 이라 그 자리에서 멈춘다.
    private var pulseAnimation: Animation? {
        guard !feedback.isReady, !reduceMotion else { return nil }
        return .easeInOut(duration: 0.9).repeatForever(autoreverses: true)
    }
```

- **`feedback.isReady` 가 `true` 가 되는 순간 `pulseAnimation` 이 `nil`** 이 되어 맥동이 멈추고 글자가 또렷해진다. 따로 끄는 코드가 필요 없다
- 실패해서 영영 안 오면 계속 맥동한다 — 그건 **다음에 고칠 자리를 스스로 알려 주는 것**이라 그대로 둔다

## 확인

- **직접입력을 틀린다** → 창이 뜨고 글자가 숨 쉬듯 밝아졌다 어두워지는가
- **해설이 도착하면** 맥동이 멈추고 또렷해지는가
- 설정 → 손쉬운 사용 → **동작 줄이기**를 켜면 맥동 없이 옅게만 뜨는가

## ⓐ Supabase — 앱보다 먼저

컬럼이 없으면 회차 다섯 줄이 통째로 거부된다 (8/31).

```sql
begin;

alter table public.obs_record add column explanation_source text;

drop policy "app can insert only" on public.obs_record;

create policy "app can insert only" on public.obs_record
for insert to anon
with check (
    question_id >= 1 and question_id <= 100000
    and mode_raw >= 0 and mode_raw <= 3
    and sec_to_submit >= 0 and sec_to_submit < 3600
    and (sec_to_first_touch is null
         or (sec_to_first_touch >= 0 and sec_to_first_touch <= sec_to_submit))
    and asked_at > now() - interval '30 days'
    and asked_at < now() + interval '1 day'
    and length(device_id) >= 8 and length(device_id) <= 64
    and (chosen is null or length(chosen) <= 100)
    and (reason is null or length(reason) <= 300)
    and (explanation is null or length(explanation) <= 500)
    and (explanation_source is null or explanation_source in ('cloud', 'device'))
);

commit;
```

## ⓒ `KCT/Grading/CommentaryWriter.swift`

**해설과 「어디서 왔는지」를 함께 돌려준다.** `Commentary` 아래에 새 타입.

```swift
/// 해설과 그것을 만든 곳.
struct WrittenCommentary {
    let text: String
    /// `"cloud"` 또는 `"device"`. 로그에 그대로 들어간다.
    let source: String
}
```

`write(for:)` 의 선언을 바꾸고

```swift
    func write(for item: QuizItem) async -> WrittenCommentary? {
```

`let prompt = ...` 다음의 `do { ... } catch { ... }` 를 통째로 지우고 이걸 넣는다.

```swift
        if let cloud = cloudSession(instructions: instructions),
           let text = await ask(cloud, prompt: prompt, from: "cloud") {
            return WrittenCommentary(text: text, source: "cloud")
        }

        guard let text = await ask(
            LanguageModelSession(instructions: instructions),
            prompt: prompt,
            from: "device")
        else { return nil }

        return WrittenCommentary(text: text, source: "device")
```

그리고 `write(for:)` 아래에 함수 둘.

```swift
    /// 구름 모델 세션. 쓸 수 없으면 `nil` 이고 부르는 쪽이 기기 모델로 간다.
    ///
    /// `isAvailable` 과 `quotaUsage` 를 미리 보는 이유 — 오류를 받고 물러나면
    /// 그만큼 어머니가 기다립니다. 물러날 것은 부르기 전에 알 수 있습니다.
    private func cloudSession(instructions: String) -> LanguageModelSession? {
        guard !Self.forcesDeviceModel else { return nil }
        guard #available(iOS 27, *) else { return nil }

        let cloud = PrivateCloudComputeLanguageModel()
        guard cloud.isAvailable, !cloud.quotaUsage.isLimitReached else { return nil }

        return LanguageModelSession(model: cloud, instructions: instructions)
    }

    /// 세션 하나에 물어보고 문장을 받아 온다. 실패하면 이유를 찍고 `nil`.
    ///
    /// `from` 을 받는 이유 — 콘솔에서 **구름이 실패한 것인지 기기가 실패한 것인지**
    /// 갈라야 합니다. 오류를 통째로 버려서 「잠시만 같이 살펴봐요.」가 남는 이유를
    /// 못 찾았던 것이 2026-09-05 입니다.
    private func ask(
        _ session: LanguageModelSession,
        prompt: String,
        from place: String
    ) async -> String? {
        do {
            let response = try await session.respond(to: prompt, generating: Commentary.self)
            let text = response.content.text.trimmingCharacters(in: .whitespacesAndNewlines)
            return text.isEmpty ? nil : text
        } catch {
            print("❌ 해설 실패(\(place)):", error)
            return nil
        }
    }
```

> `forcesDeviceModel` 은 6단계에서 만든다. **5단계만 먼저 빌드하려면 그 줄을 잠시 빼고 넣는다.**
>
> **이름이 바뀌었을 수 있다.** `PrivateCloudComputeLanguageModel`·`isAvailable`·`quotaUsage` 는 발표 시점의 이름이다. Xcode 자동완성으로 확인하고 넣는다.

# 8단계 — 답을 고르는 순간 낭독을 멈춘다

> 2026-09-06 추가. 빠르게 답하면 소리가 계속 흘러 결과 화면까지 따라온다.

## 왜

낭독은 **「이제 당신 차례입니다」라는 신호**다. 그런데 어머니가 신호가 끝나기 전에 답하시면, 소리가 다음 문제까지 넘어가고 결과 화면에서도 흘러나온다. **이미 지나간 문제를 읽고 있는 것**이라 지금 무엇을 하는 중인지 헷갈리게 만든다.

멈춰야 할 자리가 둘이다.

```
답을 고른 순간          → 읽던 문제는 이미 다 읽은 셈이다
읽을 문제가 없어진 순간  → 결과 화면 · 「결과를 정리하고 있어요」
```

`speak(_:)` 는 이미 **읽던 것을 멈추고 새로 읽는다.** 그래서 「다음 문제로 넘어갈 때」는 지금도 안 겹친다. 없는 것은 **그냥 멈추기**다.

## ① `KCT/DesignSystem/SpeechReader.swift` — 멈추는 입구를 만든다

`speak(_:)` 아래에.

```swift
    /// 읽던 것을 곧바로 멈춘다.
    ///
    /// 답을 고른 순간과 읽을 문제가 없어진 순간에 부릅니다.
    /// ``speak(_:)`` 도 첫 줄에서 같은 일을 하지만, 그쪽은 **새로 읽기 위해** 멈추는 것이라
    /// 「그냥 멈추기」에는 쓸 수 없습니다.
    func stop() {
        synthesizer.stopSpeaking(at: .immediate)
    }
```

## ② `KCT/Screens/QuizView.swift` — 답을 고르면 멈춘다

`.onChange(of: session?.currentIndex)` **아래**에 붙인다.

```swift
        .onChange(of: session?.hasAnswer) { _, answered in
            if answered == true { speaker.stop() }
        }
```

- `hasAnswer` 는 답이 비어 있지 않으면 참이다. **보기를 누르거나 첫 글자를 치는 순간** 거짓에서 참으로 바뀐다
- 다음 문제로 넘어가면 답이 비워져 참에서 거짓이 된다. 그때는 멈추지 않는다 — `answered == true` 만 보기 때문이다
- `Bool?` 이라 `== true` 로 비교한다. `if answered` 는 컴파일되지 않는다

**소리를 화면 층에 두는 규칙이 여기서도 지켜진다.** `QuizSession` 은 소리를 모르고, 「답이 들어왔다」는 사실만 알려 준다.

## ③ `KCT/Screens/QuizView.swift` — 읽을 문제가 없으면 멈춘다

`readAloud(_:)` 를 이걸로 교체.

```swift

            speaker.stop()
            return

```

지금은 `guard let item else { return }` 이라 **아무것도 안 하고 돌아간다.** 그래서 회차가 끝나 `current` 가 `nil` 이 되어도 읽던 소리가 그대로 남는다. 결과 화면까지 따라오는 것이 이것이다.

## 확인

1. **문제가 읽히는 도중에 보기를 누른다** → 그 자리에서 소리가 끊기는가
2. **직접입력에서 첫 글자를 친다** → 끊기는가
3. **마지막 문제를 빠르게 답한다** → 「결과를 정리하고 있어요」와 결과 화면이 **조용한가**
4. **답을 고른 뒤 「다시 읽기」를 누른다** → 다시 읽어 주는가 (멈춤이 낭독을 막아 버리면 안 된다)

4번이 이 단계에서 깨지기 쉬운 자리다. 「다시 읽기」는 `hasAnswer` 를 바꾸지 않으므로 멈춤이 안 걸려야 맞다.

## 남겨 둔 것

## 무엇이 꼬였나

### 겹치는 길

한 문항 안에서는 채점 → 해설이 차례로 돈다. 겹치지 않는다. **문항 사이가 문제다.**

```
q3 오답 → 모달이 뜬다 → 해설을 만드는 중 …
                          ↓ 「다음 문제」를 바로 누름 (카운트다운을 없앴으니 즉시 가능)
                       q4 로 넘어감
q4 답 제출 → 채점 시작        ← q3 의 해설이 아직 돌고 있다
```

`dismissFeedback()` 은 **해설을 기다리지 않는다.** 기다리면 안 되기도 한다 — 어머니를 붙잡아 둘 이유가 없다. 그래서 **떠난 뒤에도 해설은 계속 만들어진다.**

그 상태에서 다음 문항이 직접입력이면 `LanguageModelSession` 이 둘이 된다. 온디바이스 모델은 이걸 못 견딘다. **먼저 잡은 쪽이 이기고 나중 쪽이 안 돌아온다.**

증상이 두 가지였던 것이 이 설명과 맞는다.

| 언제 | 멈춘 곳 | 그때 돌고 있던 것 |
|---|---|---|
| 9/6 오전 | 「채점 중이에요」 버튼 | 앞 문항의 **해설** |
| 9/6 오후 | 「잠시만 같이 살펴봐요.」 | 앞 문항의 **해설**(또는 채점) |

### 지금 구조가 이걸 못 견디는 이유 둘

❌ 해설 실패: May contain unsafe content
```

**애플의 안전 필터(guardrail)다.** 모델이 안 돌아온 것이 아니라 **곧바로 거부한 것**이다. 위의 「겹침」 가설은 이 증상에는 **틀렸다.**

- 거부는 즉시 온다. 그러니 「잠시만 같이 살펴봐요.」가 남은 것은 **기다려서가 아니라 `nil` 이 왔는데 창을 안 갈아 끼워서**다 → ④가 고친다
- 무엇이 걸렸는지는 아직 모른다. 일제강점기·전쟁·식민지 같은 낱말이 의심스럽다. **문항별로 어느 것이 걸리는지 세어 봐야** 한다
- **PCC 로 옮겨도 안전 필터는 그대로일 수 있다.** 완화하는 설정이 있는지는 확인하지 못했다

그래도 **관문과 시한은 그대로 넣는다.** 「채점 중이에요」에서 멈춘 것은 아직 설명되지 않았고, 그건 거부(즉시)가 아니라 **안 돌아온 것**이었다. 원인이 둘일 수 있다.

//  KCT
//
//  역할 : 온디바이스 모델 호출을 한 줄로 세우고, 시한을 넘으면 포기한다

//
//  ── 구성 ──────────────────────────────────────────────
//  ModelGate
//  ├─ run(seconds:_:)   앞 차례가 끝난 뒤 실행하고, 시한을 넘으면 nil
//  └─ tail              마지막으로 세운 차례. 다음 사람이 이걸 기다린다
//
//  ── 연결 ──────────────────────────────────────────────
//  불러 쓰는 곳 : MeaningGrader(채점) · CommentaryWriter(해설)
//  기대는 것    : 없음
//  건드리지 않는 것 : 실패를 어떻게 보여줄지 — 부르는 쪽이 정한다
//

import Foundation

/// 온디바이스 모델을 한 번에 하나씩만 쓰게 하는 관문.
///
/// 겹쳐 부르면 나중 호출이 아예 돌아오지 않습니다. 2026-09-06 에 직접입력에서
/// 두 번 멈췄고, 둘 다 앞 문항의 해설이 아직 돌고 있을 때였습니다.
///
/// - Important: 시한을 넘으면 `nil` 입니다. **틀리게 채점되는 것보다 멈춰 있는 것이
///   훨씬 나쁩니다** — 틀린 채점은 다음 회차에 회복되지만, 멈춤은 회차를 끝냅니다.
@MainActor
enum ModelGate {

    /// 마지막으로 세운 차례. 새로 온 호출은 이것이 끝나기를 기다린다.
    private static var tail: Task<Void, Never> = Task {}

    /// 앞 차례가 끝난 뒤 실행한다. 시한을 넘기면 `nil`.
    static func run<T: Sendable>(
        seconds: Double,
        _ work: @escaping @Sendable () async throws -> T
    ) async -> T? {
        let previous = tail

        let job = Task { () -> T? in
            await previous.value
            return await race(seconds: seconds, work)
        }
        tail = Task { _ = await job.value }

        return await job.value
    }

    /// 일과 시계를 함께 출발시키고, 먼저 끝난 쪽을 받는다.
    private static func race<T: Sendable>(
        seconds: Double,
        _ work: @escaping @Sendable () async throws -> T
    ) async -> T? {
        await withTaskGroup(of: T?.self) { group in
            group.addTask { try? await work() }
            group.addTask {
                try? await Task.sleep(for: .seconds(seconds))
                return nil
            }

            let first = await group.next() ?? nil
            group.cancelAll()
            return first
        }
    }
}
```

# 10단계 — 채점 지침을 통째로 다시 쓴다

> 2026-09-06. 「고죠선」이 「고조선」의 정답으로 통과했다.

## 왜 넓어졌나

지금 지침의 **첫 문단**이 원인이다.

```
사용자는 어르신이고 음성이나 손으로 답합니다.
말버릇과 띄어쓰기는 무시하고, 무엇을 답으로 골랐는지만 보세요.
```

「무엇을 골랐는지만 보라」는 **「소리가 비슷하면 그거겠지」로 읽힌다.** 아래 여섯 규칙이 아무리 엄격해도 **첫 문단이 관대하면 그쪽이 이긴다.** 「띄어쓰기만 다르다」가 「비슷하면 통과」로 넓어진 것도 같은 뿌리였다.

그래서 규칙을 더 붙이지 않고 **처음부터 다시 쓴다.** 두 가지를 바꾼다.

- **첫 문단부터 「글자를 비교하라」로 시작한다.** 관대함을 부르는 문장을 아예 없앤다
- **판단이 아니라 절차로 시킨다.** 「이게 같은 것인가?」는 흔들리지만 「군더더기를 지우고 → 공백을 지우고 → 글자를 맞춘다」는 흔들리지 않는다

## 그런데 — 이걸 모델이 해야 하나

위 절차를 다시 읽어 보면 **전부 코드로 할 수 있는 일**이다.

```
1단계 군더더기 지우기   → 목록에 있는 말을 지운다
2단계 공백·문장부호 지우기 → 코드 한 줄

```

**모델이 정말 필요한 자리는 「세종 = 세종대왕」 같은 다른 이름을 봐주는 것뿐인데, 우리는 그걸 오답으로 두기로 이미 정했다.** 그러면 모델을 쓸 이유가 거의 없다.

코드로 옮기면 얻는 것이 넷이다.
